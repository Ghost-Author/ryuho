Hexo 主题很容易停留在“能展示文章”的阶段：首页列出标题，文章页渲染 Markdown，再补一个归档和标签页。这样的骨架可以使用，却很难回答这是一个怎样的站点、作者长期关注什么、读者应该从哪里开始。

这个博客没有继续堆叠第三方主题配置，而是围绕现有 `themes/minimal` 逐步改造。目标不是做出更复杂的视觉效果，而是让界面真实表达内容定位：AI 工程、系统思考和博客工程化实践，并让搜索、专题、项目、归档与文章阅读形成连续路径。

## 先让首页承担定位，而不是只承担列表

通用博客首页往往把最新文章放在最显眼位置，但第一次访问的人还不知道这些文章为什么值得读。

当前首页最前面直接输出：

```text
IT 个人博客 · AI 工程 · 系统思考
```

标题和副标题之后提供两个明确入口：阅读最新文章、浏览技术分类。搜索框和 RSS 也在首屏出现，对应“寻找已有内容”和“持续接收更新”两种需求。

这不是营销式首页。它没有把文章藏在多屏介绍之后，紧接着就是“刚刚更新”、专题路径、技术索引和文章列表。首页要表达身份，但博客的主体仍然是内容。

## 最新文章不是一个标题，而是一段阅读决策信息

首页通过 `site.posts.sort('date', -1)` 找到最新文章，并组合：

- 发布日期；
- 按正文长度估算的阅读时间；
- 标题与 description；
- 文章标签；
- 明确的继续阅读入口。

阅读时间按去除 HTML 后的字符数除以 500 估算，至少显示一分钟。这不是精密统计，而是稳定、可解释的提示。它帮助读者判断当前是否适合打开长文，同时不引入外部脚本。

description 优先于正文截取，意味着作者写下的内容概括会贯穿首页、搜索和分享场景。主题不只是展示内容，也在推动内容字段真正被使用。

## 专题页解决“按什么顺序读”

标签和分类适合聚合，却无法表达文章之间的先后关系。于是首页增加“专题路径”，当前包含 AI 工程上线路径和博客工程化实践。

专题页不是自动生成的标签列表，而是手工维护的阅读路线。这样可以把“评测集、RAG、智能体、可观测性”组织成一条工程顺序，也可以把博客从定位、搜索、离线、图片、推荐到双部署的改造串成完整复盘。

这里的取舍很明确：

- 自动列表维护成本低，但只能按日期或标签排序。
- 手工专题需要更新，却能表达作者对知识结构的判断。

主题提供入口和视觉层级，内容页面负责真正的编排，两者没有被强行塞进一个复杂组件。

## 技术索引要帮助扫描，而不是制造标签云

标签数量增长后，传统标签云会因为字号差异形成视觉噪声，也未必能突出站点定位。

首页先按一组主题优先级排列标签和分类，例如 AI 工程、RAG、智能体、评测、工程实践、Hexo、CI/CD 和 SEO；不在优先列表中的项目再按文章数量排序。

这是一种编辑型排序。它承认“最常出现”不一定等于“最应该代表本站”。界面通过名称与数量的紧凑列表呈现，读者可以快速扫描，而不是从装饰性的字号大小里猜测重点。

排序规则留在模板中也有代价：每次定位变化都需要修改主题。当前站点规模下，这比引入额外配置层更直接；当方向列表需要频繁运营时，再迁移到主题配置更合适。

## 文章页围绕阅读过程补齐信息

文章页不只渲染 Markdown。顶部根据实际正文计算字数和阅读时间，显示发布日期与更新日期；正文有目录，页面顶部有阅读进度；文章操作提供复制链接和返回归档。

正文之后的相关推荐根据共享标签和分类计分：

- 每个相同标签加 2 分；
- 每个相同分类加 1 分；
- 分数相同时按日期倒序；
- 最终选择 3 篇。

如果没有共同主题，仍会回退到最近更新，并在界面上明确标记。这套算法很简单，但比随机推荐更符合技术文章阅读路径，也不需要行为追踪。

文章底部还重复提供字数、阅读时间、分类以及首页和标签入口。长文读完后，读者不必滚回顶部才能继续浏览。

## 全局布局统一处理可访问性与分享信息

`layout.ejs` 承担所有页面共同的发布能力。

页面 description 优先读取 front matter，再从正文回退，并压缩空白、限制长度。canonical 根据页面 permalink 或 path 生成；封面同时进入 Open Graph、Twitter Card 和 JSON-LD。文章标签会输出为 `article:tag`。

交互层面还包括：

- “跳到正文”的 skip link；
- 主内容区域可接收焦点；
- 根据系统偏好和本地保存值初始化明暗主题；
- Service Worker 注册失败时不阻塞页面；
- 回到顶部按钮和阅读进度；
- 图片明确 width、height 与解码策略。

这些能力放在统一布局中，避免每一种页面各自实现，也让审计器可以按页面性质验证最终输出。

## 为什么保留自己的轻量主题

成熟主题通常提供更多开关、插件和布局，直接采用它们完全合理。当前项目继续维护 `minimal`，主要因为它已经和内容模型形成了具体耦合：

- 首页知道两个真实专题；
- 文章页了解标签与分类的推荐权重；
- SEO 与双部署路径统一使用 Hexo helper；
- 搜索、项目页和专题页共享现有视觉语言；
- 评论只有在配置完整时才启用；
- 分析脚本同样由配置决定是否输出。

代价是每项能力都要自己验证，升级 Hexo 时也需要检查模板兼容性。好处则是界面没有大量不用的功能，任何模块为什么存在都可以从内容需求解释。

## 视觉改造中的克制

个人表达不等于把页面填满个性装饰。技术博客首先需要稳定阅读，所以改造遵循几条约束：

- 正文优先，装饰不进入核心阅读区域；
- 列表信息足够密集，但每项保持清楚层级；
- 专题和项目使用明确入口，不依赖隐藏菜单；
- 明暗主题都保持可读；
- 移动端不假设存在宽屏侧栏；
- 图片尺寸提前声明，减少布局变化。

首页保留了个人简介、当前关注和站点入口，但它们处于内容发现路径之后，没有抢占文章的主体地位。

## 如何验证主题改造

模板能渲染只是第一步。当前审计会检查：

- 所有页面的 description、canonical 与 Open Graph URL；
- 首页最新文章入口是否指向真实文章；
- 专题、项目、搜索和归档是否可达；
- 文章分享信息和相关推荐是否存在；
- 图片是否声明尺寸；
- HTML 是否泄漏空值或占位配置；
- GitHub Pages 与 Vercel 两种 root 下链接是否成立。

自动审计之外，视觉和交互仍需浏览器人工检查。机器可以确认目录存在，却不能判断目录在窄屏下是否舒服；可以确认按钮有链接，却不能证明信息层级自然。

## 可复用的结论

改造主题时，与其先问“还能加什么组件”，不如依次回答：

1. 第一次访问的人能否理解站点定位？
2. 读者能否找到最新内容、专题路径和历史文章？
3. 文章页是否支持从打开到读完的完整过程？
4. 元数据能否服务搜索、分享和相关推荐？
5. 所有能力能否在真实部署路径下验证？

一个好的个人主题，不需要看起来和所有网站都不同。它更重要的价值，是让作者的内容结构和长期判断在页面上自然显现。
