Hexo 生态里有许多成熟主题。它们通常拥有更丰富的配置、完整文档、社区反馈和经过大量站点验证的兼容性。对于希望尽快上线、偏好标准博客结构，或者不想长期维护前端代码的人，直接选择成熟主题往往是更稳妥的决定。

这个博客没有直接套用一套成熟主题，并不是因为现有主题“不够好”，也不是为了从头造一个更复杂的轮子。真正原因是需求逐渐集中在几个很具体的方向：技术内容的信息架构、零 CDN 依赖、GitHub Pages 与 Vercel 双路径、构建期相关推荐，以及能够被本地审计完整覆盖的页面结构。

当这些需求成为站点长期维护的一部分时，本地主题带来的控制权比配置项数量更重要。

## 先区分“换皮肤”和“维护产品界面”

如果主题只负责字体、颜色和文章排版，那么换一个成熟主题完全合理。

但当前 `themes/minimal` 承担的不只是视觉样式。首页会读取最新文章、专题、标签和分类；文章页会计算字数、阅读时间和相关推荐；全局布局会生成 canonical、Open Graph、Twitter Card 与结构化数据；脚本还提供主题切换、阅读进度、代码复制和内容搜索。

也就是说，主题已经参与了内容发现、连续阅读、SEO 和发布质量。它更接近这个博客的产品界面，而不是一层可以随时替换的皮肤。

一旦主题承担这些责任，选择标准就会发生变化。判断重点不再只是截图是否漂亮，而是它能否准确表达当前内容结构，并且在两种部署环境中保持一致。

## 需求一：让首页围绕内容组织，而不是围绕组件组织

这个博客聚焦 AI 工程、工程实践和系统思考。首页需要先回答三个问题：

- 站点主要写什么；
- 最近更新了什么；
- 如果想系统阅读，应该从哪里开始。

因此首页把最新文章、专题路径、技术索引、写作方向和时间线组织在一起。文章、标签和分类的数量直接来自 Hexo 数据；最新文章按钮也指向真实文章，而不是固定落到归档页。

成熟主题当然也能实现类似页面，有些甚至提供了更多模块。但引入后通常需要接受它原有的信息层级，或者通过大量配置和覆盖样式重新调整。当希望首页严格服务既定内容策略时，直接维护较小的 EJS 模板更容易知道每一块为什么存在。

这里的目标不是“页面独一无二”，而是减少与内容无关的模块。

## 需求二：文章页需要可解释的连续阅读

当前文章页不只渲染 Markdown。它还提供目录、封面、标签、复制链接、上一篇与下一篇、文章事实和相关推荐。

相关推荐的规则写在本地模板中：共享标签获得更高权重，共享分类提供补充权重，同分时优先较新的文章；没有主题交集时退化为最近更新。读者看到的“同主题”或“最近更新”与实际计算一致。

这个规则很简单，却和当前内容组织方式高度绑定。如果使用成熟主题内置的推荐功能，需要先理解它的匹配逻辑、配置入口和退化行为；如果主题没有该能力，还要通过注入或插件补齐。

本地实现的价值在于可解释和可验证。规则有变化时，可以直接修改拥有这项责任的模板，并让构建审计确认每个文章页仍然包含相关推荐。

## 需求三：前端依赖要尽量留在仓库里

搜索功能是一个典型例子。

站点没有从 CDN 加载 Lunr.js 或其他搜索库，而是在构建阶段生成 `search-index.json`，浏览器使用本地 JavaScript 完成检索。审计还会扫描 HTML，阻止 unpkg 和 jsDelivr 这类临时 CDN 依赖重新进入页面。

这并不是说 CDN 或成熟库不可用。它们在很多项目中能降低开发成本，也可能提供更成熟的分词与排序。当前选择只是基于博客规模和维护目标：简单检索已经能满足内容发现，没有必要为暂时不存在的问题引入额外网络依赖。

主题代码完全留在仓库后，站点的核心阅读流程不会因为第三方脚本不可用而失效，版本变化也能和内容、脚本一起进入同一个提交。

## 需求四：两种部署根路径必须是一等公民

GitHub Pages 把站点放在 `/ryuho/`，Vercel 则部署在 `/`。这不是仅改一个首页链接就能解决的问题，canonical、manifest、service worker、搜索索引、CSS、脚本和文章链接都必须理解当前 root。

本地主题统一使用 Hexo 的 `url_for` 与 `full_url_for` 生成路径，配合构建脚本根据当前配置生成 robots 和 manifest。发布前再运行两套检查：

```bash
npm run check
npm run check:vercel
```

成熟主题通常也支持 `root`，这本来就是 Hexo 的标准能力。但当站点还叠加了自定义搜索、专题、PWA 和审计规则时，问题已经超出主题默认页面。把模板和生成器放在同一仓库，能让路径责任保持一致，而不需要追踪多层主题覆盖。

## 需求五：可访问性和阅读细节需要直接落在模板里

全局布局提供“跳到正文”链接和明确的主内容锚点；按钮维护 `aria-label` 与状态；页面响应系统深浅色偏好，也尊重减弱动画设置。文章图片声明尺寸以减少布局移动，表格在窄屏中包装为可横向滚动区域，外链统一补充安全属性。

这些能力未必比成熟主题更多。成熟主题往往经过更广泛的浏览器和辅助技术验证，本地主题反而需要自己承担测试责任。

选择本地维护，是因为这些细节可以和本项目的审计规则一一对应。例如审计会检查所有 HTML 图片是否声明宽高、关键页面是否包含描述与 canonical、404 是否带 `noindex`。界面实现和质量门禁之间没有黑盒。

## 本地主题的代价不能被忽略

控制权不是免费的。

首先，模板、样式和前端脚本都要自己维护。Hexo 或浏览器行为变化时，没有上游主题替你集中修复。其次，本地实现得到的真实站点验证范围远小于流行主题，边缘兼容问题更依赖主动测试。最后，功能很容易越写越多，最终变成一套只有自己能理解的框架。

所以这个主题刻意保持较小：

- 不维护复杂插件系统；
- 不为每个视觉细节增加配置；
- 不启用缺少完整配置的评论组件；
- 不加入没有内容承载计划的新栏目；
- 新功能必须服务明确阅读需求并通过审计。

本地主题不是为了追求“所有东西都自己写”，而是把需要长期负责的部分控制在可理解范围内。

## 什么情况下我会推荐成熟主题

如果目标是尽快开始写作，成熟主题应该优先考虑。尤其在以下场景中，它的收益很高：

- 页面结构接近标准博客；
- 不需要特殊专题和项目路径；
- 希望使用成熟评论、相册或多语言能力；
- 没有时间维护响应式样式和可访问性；
- 更看重社区文档与升级支持。

好的工程选择并不要求每个人走同一条路。主题是否成熟、本地实现是否自由，都不是单独决定质量的标签。关键是需求、维护能力和生命周期是否匹配。

## 如何验证这个选择仍然合理

本地主题每次改动后，都必须通过构建产物验证。

审计会检查 SEO、内部链接、静态资源、专题与项目入口、文章元数据、相关推荐和模板值泄漏；GitHub Pages 与 Vercel 两套配置都要生成成功。人工检查则关注自动脚本不擅长判断的部分，例如移动端阅读是否拥挤、标题层级是否自然、界面是否抢走正文注意力。

如果未来大部分维护时间都消耗在主题兼容，而内容需求已经可以被成熟主题直接满足，那么重新评估迁移同样合理。控制权应该服务项目，而不是成为必须捍卫的身份。

## 结论

没有直接使用成熟 Hexo 主题，是这个博客在特定需求下做出的范围选择：信息架构与内容策略紧密结合，核心依赖留在本地，双部署路径统一处理，页面能力可以进入同一套质量审计。

成熟主题提供的是经过验证的通用能力，本地主题提供的是对当前需求的直接控制。两者没有高下之分。对这个项目来说，一套足够小、能够完整理解并持续验证的主题，比一套功能更多但需要反复覆盖的主题更合适。
