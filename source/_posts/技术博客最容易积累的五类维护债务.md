技术博客的维护债务很少以一次严重故障的形式出现。它更像一组逐渐失真的小问题：新文章沿用空模板，旧链接悄悄失效，主题依赖的外部脚本不再稳定，两个部署环境得到不同结果，首页又多了一个没有内容支撑的入口。

这些问题单独看都不紧急，所以很容易被推迟。但它们会持续增加下一次写作和发布的成本，最后让“写一篇文章”变成一场对配置、模板和历史遗留的排查。

结合这个 Hexo 博客当前的结构，可以把最常见的维护债务归纳为五类。它们不只存在于 Hexo，也适用于大多数长期运行的内容站点。

## 第一类：内容债务

内容债务不是“文章数量不够”，而是文章缺少继续被使用的条件。

常见表现包括：

- 标题存在，但 description 只是空值或泛泛一句话；
- 标签随手创建，同义词不断分裂；
- 分类缺失，文章无法进入稳定路径；
- 正文只有提纲，没有背景、方案和验证；
- 示例文章、默认欢迎页或空日记长期留在线上；
- 观点已经变化，却没有更新说明或后续文章。

这类债务会影响首页摘要、搜索索引、相关推荐、分享卡片和专题组织。也就是说，一处元数据偷懒，会在多个产品表面同时留下缺口。

当前项目把一部分内容标准放进了 `tools/audit-site.js`：每篇文章必须有 title、date、足够具体的 description、至少两个 tags、至少一个 category、真实 cover，并且正文不能短到只剩占位符。脚手架也接受检查，避免每次新建文章都从空字段开始。

机器只能确认“字段存在”和“正文不是空壳”，不能判断观点是否可信。因此偿还内容债务还需要人工规则：文章说明问题背景，给出明确边界，记录实现或方法，最后交代如何验证。无法由仓库事实支持的经历和数据，不因为叙事需要就补上。

## 第二类：链接与信息架构债务

内容站点会不断增加入口：归档、标签、分类、专题、项目、搜索、上一篇、下一篇和相关推荐。每增加一种组织方式，就增加一组可能失效的关系。

最直观的债务是 404，但更隐蔽的问题包括：

- 首页按钮仍然指向已经改变的路径；
- sitemap 列出不存在的页面；
- canonical 带有重复子路径；
- GitHub Pages 正常，Vercel 上的静态资源却指向错误位置；
- 专题列出文章标题，但文章改名后链接没有同步；
- 相对路径在当前页面可用，换一层目录后失效。

这个项目同时部署到 `/ryuho/` 和 `/`，路径债务尤其容易暴露。处理方式不是要求作者每次人工记住前缀，而是让模板统一使用 Hexo helper，让 robots、manifest 和 service worker 根据当前配置生成。

构建后的审计会扫描全部 HTML 中的 `href` 与 `src`，把站内 URL 映射回 `public` 目录，确认目标文件或目录真实存在；sitemap 的每个目标也会再次验证。

偿还这类债务的关键，是在最终产物上检查关系，而不只是确认源模板语法正确。静态站所有页面都已生成，因此全量链接验证成本并不高。

## 第三类：依赖与资源债务

前端功能很容易通过“加一个库”迅速完成。搜索、代码高亮、评论、统计、图片处理和动画都有现成方案。但每个依赖都会带来版本、安全、网络和升级责任。

依赖债务不等于依赖数量多，而是项目已经说不清：

- 这个库解决什么真实问题；
- 它是否属于核心阅读路径；
- 外部服务不可用时会发生什么；
- 版本由谁锁定；
- 是否存在更小的本地实现；
- 删除它会影响哪些页面。

当前博客的搜索索引由本地生成器创建，前端不依赖临时 CDN；审计明确阻止 unpkg 和 jsDelivr 链接进入 HTML。图片优化使用已锁定的 `sharp`，只操作构建产物，并且只有压缩后更小时才替换原结果。

这不意味着所有依赖都应该自己实现。Hexo、渲染器、feed、sitemap 和 Sharp 都是成熟工具，自己重写反而会扩大风险。更合理的原则是：核心领域使用成熟依赖，站点特有且足够简单的逻辑留在本地；每项依赖都能说清收益和失败边界。

资源债务还包括图片格式与尺寸。扩展名可能和真实 MIME 不一致，缺少宽高会造成布局移动，原图直接发布会增加传输体积。审计真实文件签名、HTML 尺寸声明和构建后优化，能把这些问题从视觉抽查变成确定规则。

## 第四类：构建与部署债务

“我的电脑可以生成”不是可维护的发布流程。

构建债务常从几处出现：

- 本地使用一个命令，CI 使用另一个命令；
- 锁文件存在，部署却运行非确定性的安装方式；
- 生成步骤和图片优化顺序不一致；
- 不同平台各维护一套重复配置；
- 发布分支与源码分支职责混淆；
- 构建成功，却没有检查结果是否可用。

这个项目把 GitHub Pages 和 Vercel 的差异限制在 `url` 与 `root`。GitHub Actions 从 `main` 获取源码，使用 `npm ci` 安装锁定依赖，运行 `npm run check` 后发布 `public`；Vercel 合并 `_config.yml` 和 `_config.vercel.yml`，运行 `npm run build:vercel`。

两条路径最终使用同一个审计脚本。这样，平台差异不会扩散成两套主题、两套搜索或两套 SEO 文件。

值得注意的是，`gh-pages` 只是生成后的静态产物分支，不包含 Hexo 源码和 `package.json`。如果 Vercel 错连这个分支，构建环境甚至找不到预期的 `public` 输出流程。README 把这一点明确记录下来，就是在偿还“只有维护者记得”的知识债务。

## 第五类：界面与功能债务

博客最容易被功能债务拖累，因为新增一个组件通常比删除它更有成就感。

评论、统计、点赞、相册、动态背景、社交卡片和更多首页模块都可以让站点看起来更完整。但如果没有真实使用场景，它们会留下配置、样式、隐私、可访问性和第三方可用性问题。

当前维护策略明确规定：优先级依次是内容、可靠性、阅读体验和新功能；没有真实场景的社交、评论或统计组件默认不做；不增加仅用于装饰的动画、卡片和视觉元素；没有内容计划就不创建新栏目。

已经保留的交互都围绕阅读任务：深浅色模式、跳到正文、阅读进度、目录、代码复制、表格滚动、链接复制和回到顶部。评论模板虽然具备接入条件，但配置未完整时保持关闭，审计还会阻止占位 ID 出现在页面中。

界面债务的偿还方式不是周期性“重做设计”，而是定期追问每个模块服务什么任务。回答不出来的功能，即使代码仍能运行，也应该进入删除候选。

## 五类债务为什么会互相放大

维护债务很少孤立存在。

一篇缺少标签的文章，会降低搜索和相关推荐质量，这是内容债务传导到产品功能；一个写死的资源路径，会在另一部署环境失效，这是界面实现传导到部署债务；一个外部评论脚本，会同时引入依赖、隐私、性能和样式责任。

因此，偿还债务不能只靠某次“大扫除”。更有效的方式是把规则放到日常发布入口：

```bash
npm run check
npm run check:vercel
```

审计适合守住确定性底线，维护策略则处理机器无法判断的范围问题。前者阻止错误进入产物，后者阻止没有依据的需求进入代码。

## 建立一份可执行的债务清单

可以按以下顺序定期检查：

1. 内容是否有完整元数据和可验证结论；
2. 所有站内入口和 sitemap 是否可达；
3. 每项依赖是否仍有明确用途和锁定版本；
4. 本地、CI 与两个部署平台是否运行同一套核心流程；
5. 每个界面模块是否仍然服务阅读或内容发现。

这份清单不要求一次解决所有问题。优先处理会阻塞发布、破坏链接或误导读者的债务，再处理性能和体验，最后才考虑新功能。

## 结论

技术博客的维护债务主要积累在内容、链接、依赖、构建和功能五个方向。它们共同的根源，是某项责任只存在于记忆里，没有进入结构、文档或自动验证。

长期维护不是永远增加能力，而是持续缩短“发现问题到确认修复”的路径。让内容标准进入脚手架，让路径进入产物审计，让部署差异收敛到配置，让功能范围写进维护策略，博客才不会随着文章增加而越来越难发布。
