为静态站点增加审计脚本时，最容易采用的做法是不断追加判断：这个文件应该存在、那个标签不能缺少、某段文本不能出现。规则少的时候很有效，规则多起来后，脚本可能变成一组互不相关的正则，既难解释，也不知道遗漏了什么。

这个博客的 `tools/audit-site.js` 同样从简单检查开始，后来逐步覆盖构建产物、文章源码、页面元数据、内部链接、图片和双部署路径。回头看，真正值得复用的不是某一条正则，而是一套检查模型：先确认审计对象，再定义可证明的约束，最后为每次失败保留足够的定位信息。

## 审计对象不是源代码，而是发布契约

Hexo 构建成功只能证明模板可以执行，并不证明生成结果符合发布要求。审计器因此同时观察三类对象。

第一类是源码。文章 Markdown 必须有标题、日期、描述、标签、分类和封面，正文也不能只是提纲。脚手架要提供相同的最低字段，否则每次新建文章都会制造一份待补全的半成品。

第二类是构建产物。首页、404、订阅源、站点地图、搜索索引、Service Worker、专题页和静态资源必须真实出现在 `public` 中。SEO 标签、图片尺寸和相关文章模块也只有检查最终 HTML 才有意义，因为模板分支可能让源码中存在的代码没有真正输出。

第三类是对象之间的关系。页面里的链接是否指向真实目标，Sitemap 中的地址是否可达，Manifest 声明的图标类型是否和文件签名一致，都不是单个文件可以独立回答的问题。

这三类对象构成了发布契约：

```text
内容源码 -> Hexo 构建 -> 静态产物 -> 页面与资源关系
```

只审计其中一层，都会留下明显盲区。

## 第一层检查存在性，而不是内容质量

审计器维护了一份 `requiredFiles` 清单，用于确认核心能力没有在改模板或生成器时消失。这里适合放“缺少就一定不能发布”的文件，而不是把所有生成文件都列进去。

例如，`search-index.json` 缺失意味着搜索必然不可用；某一篇历史文章没有单独列入清单，因为它已经可以通过链接和 Sitemap 的关系检查覆盖。

存在性检查的边界很重要。文件存在，只能证明生成步骤执行过，不能证明内容正确。`robots.txt` 中出现 `Sitemap:` 不代表地址没有重复 `/ryuho/ryuho/`，Manifest 有 icons 数组也不代表图标真的存在。审计器需要把“存在”和“正确”拆成不同规则，失败时才能知道是哪一层出了问题。

## 第二层检查页面必须具备的性质

对所有 HTML 页面，审计器会检查 description；除 404 外，还要求 canonical 和 Open Graph URL。文章页额外需要分享标签、分享图片和相关推荐。

这里采用的是“页面性质”而不是“模板实现”检查。审计器不关心这些标签来自哪个 EJS partial，也不绑定具体模板目录，只关心发布后的页面是否满足约束。这样即使以后重构主题，只要产物保持契约，检查就不需要同步改写。

同样的思路也用于阻止明显泄漏：

- 页面文本中不应出现独立的 `undefined` 或 `null`。
- 链接和资源属性中不应包含这两个值。
- 默认欢迎文章、空日记字段和起始模板内容不能进入产物。
- 评论配置不能残留仓库 ID 占位符。

这些规则不能判断页面是否好看，却能捕获模板变量、内容初始化和配置遗漏造成的确定性错误。

## 路径检查的核心是归一化

内部链接检查看似只是读取 `href` 和 `src`，真正困难的是把不同形式的 URL 映射到 `public` 目录。

一个站内目标可能是：

```text
/ryuho/projects/
/projects/
../search-index.json
https://ghost-author.github.io/ryuho/projects/
```

它还可能带查询参数、锚点，或者指向目录而不是具体的 `index.html`。

审计器先从 Manifest 的 `start_url` 推导站点 base，再把 URL 去除域名、查询参数、锚点和部署前缀，最终转换成相对 `public` 的路径。判断存在时同时接受：

- 完整文件；
- 目录下的 `index.html`；
- 已收集到的目录。

外部域名、邮件、电话、data URL 和页面内锚点则被明确跳过。这里不是忽略问题，而是承认本地静态产物无法可靠证明外部世界是否可用。

## 图片检查为什么读取文件签名

仅比较扩展名没有意义。一个文件可以叫 `.png`，实际内容却是 JPEG。浏览器通常仍可能显示，但 Manifest 中声明的 MIME、缓存策略和后续处理工具会得到错误信息。

当前审计器读取文件头：

- PNG 检查固定八字节签名；
- JPEG 检查 `FF D8 FF`；
- SVG 检查文本起始标记。

然后把真实类型和 Manifest 声明进行比较。页面图片还必须明确输出 width 与 height，用于稳定布局。这仍不是完整的媒体审计：它没有检查视觉清晰度、替代文本质量或不同屏幕下的裁切效果。可机器证明的格式与尺寸，应和需要人工判断的视觉质量分开。

## 失败信息是审计器接口的一部分

每条规则通过统一的 `addCheck(name, pass, detail)` 记录。最终输出 `PASS` 或 `FAIL`，失败时退出码为 1。

关键不只是让 CI 变红，而是 detail 要能帮助定位：

- 哪个 Markdown 缺少字段；
- 哪个 HTML 缺少 canonical；
- 哪个页面链接到了不存在的目标；
- 哪个图标声明类型错误；
- 哪些文件泄漏了占位内容。

为了避免日志失控，部分集合只展示前几个问题。这是一种现实取舍：CI 首屏先给出足够的首要线索，修复后再暴露后续项。审计器不是报告平台，它首先是发布阻断器。

## 什么不应该交给这套审计器

静态检查擅长回答确定性问题，却不应该伪装成内容评审或浏览器测试。

它不能可靠判断：

- 文章是否有原创观点；
- 信息架构是否符合读者习惯；
- 移动端视觉是否舒服；
- JavaScript 交互是否在真实浏览器完整运行；
- 外部链接是否长期有效；
- 搜索排序是否符合真实查询意图。

这些问题需要人工阅读、浏览器验证或另一类测试工具。把它们硬塞进同一脚本，会产生不稳定规则和虚假的安全感。

## 如何验证审计模型没有偏向单一环境

这个项目分别运行：

```bash
npm run check
npm run check:vercel
```

前者生成 GitHub Pages 的 `/ryuho/` 子路径版本，后者生成 Vercel 根路径版本，两者调用同一个审计器。相同契约在不同 URL 模型下都成立，才说明规则检查的是站点能力，而不是某一份偶然产物。

新增规则时也遵循一个简单判断：能否构造一个明确失败样例，修复后是否稳定通过。如果只能凭模糊文本猜测质量，就不该进入阻断发布的检查集合。

## 可复用的结论

一个可维护的静态站点审计器，可以按以下顺序设计：

1. 列出不可缺失的核心产物。
2. 定义每类页面必须满足的最小性质。
3. 建立 URL 到构建目录的统一归一化模型。
4. 检查源码、产物以及它们之间的引用关系。
5. 为失败结果附带具体文件和原因。
6. 把机器可证明的底线与人工质量判断分开。
7. 使用所有真实部署配置重复运行同一套契约。

规则数量不是成熟度。真正可靠的审计器，应该知道自己在证明什么，也知道哪些事情它证明不了。
