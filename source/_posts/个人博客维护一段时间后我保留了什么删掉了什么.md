个人博客刚开始搭建时，很容易把“还能增加什么”当成主要问题。首页可以再多几个模块，文章页可以加入评论和点赞，搜索可以换成更复杂的引擎，动画、统计和社交入口也都有现成方案。

维护一段时间后，更重要的问题变成了另一句：什么值得继续负责？

这篇复盘不使用“半年后”这样的时间结论，因为仓库本身无法证明一个准确维护周期；也不讨论用户量、点击率或线上事故，因为项目里没有对应数据。这里只根据当前源码、配置、README、维护策略和构建工具，说明哪些能力被保留，哪些内容已经删除、替换或保持关闭。

## 保留：以公开文章为核心的静态架构

项目继续使用 Hexo，把 Markdown、EJS 模板、配置和生成脚本转换成静态文件。

这套架构适合当前博客，因为主要任务是发布公开技术内容，而不是管理用户状态。文章、分类、标签、专题、RSS、sitemap 和搜索索引都可以在构建阶段确定，部署平台只负责分发文件。

静态架构带来的直接收益包括：

- 运行时没有数据库和应用服务需要维护；
- GitHub Pages 与 Vercel 都能承载相同产物；
- 大部分错误可以在发布前扫描 `public` 目录发现；
- 内容和站点代码都保留在同一仓库版本中。

它的限制也被保留下来：没有登录、私有内容、实时协作和可靠服务端写入。如果未来需求真正跨过这个边界，再增加后端比现在预留一套空架构更合理。

## 保留：本地、可理解的主题

当前主题位于 `themes/minimal`。它不是单纯控制颜色，而是承载首页信息架构、文章阅读流程、SEO 元数据和一组轻量交互。

首页保留最新文章、专题路径、技术索引、写作方向、时间线和 RSS 入口；文章页保留目录、标签、封面、相关推荐、上一篇与下一篇、字数、阅读时间和复制链接。

前端脚本保留深浅色切换、阅读进度、回到顶部、代码复制、标题锚点、表格滚动和外链安全处理。这些功能都有明确阅读任务，并且不依赖在线后端。

本地主题意味着兼容与测试责任也留在项目内。之所以继续保留，是因为当前规模仍能完整理解模板、样式和脚本的责任，并且它们可以接受同一套构建审计。

## 保留：构建期搜索和相关推荐

搜索没有连接在线服务。`scripts/search-index.js` 在构建时把标题、正文、摘要、日期、标签和分类写入本地 JSON，浏览器加载后完成检索。

相关推荐也没有使用行为数据。文章模板基于共享标签和分类计算简单权重，没有主题交集时退化到最近更新，并向读者展示真实原因。

这两项能力被保留，是因为它们确实降低了内容发现和连续阅读成本，同时符合静态架构边界。它们的实现也足够小：数据来自已有文章，不需要再维护账号、追踪脚本或外部索引。

如果文章规模未来明显超出单个索引的合理范围，或者检索质量成为真实问题，当前实现可以被替换。但在那之前，简单方案更容易验证。

## 保留：有限的 PWA 与离线回退

项目继续生成 Web App Manifest 和 service worker。

service worker 预缓存核心页面、专题、搜索索引、静态资源和最近文章，对同源 GET 请求采用 network-first：联网时优先返回新内容，请求失败时回退缓存。

这项能力被保留的理由不是把博客包装成原生应用，而是增加有限的网络韧性。它不会宣称所有文章永久离线可用，也没有复杂缓存版本迁移。缓存名称随构建变化，激活时清理旧缓存，让逻辑保持直接。

manifest、service worker 与当前 Hexo root 绑定生成，因此能够同时适配 GitHub Pages 的 `/ryuho/` 和 Vercel 的 `/`。

## 保留：RSS、SEO 和可访问性基础

RSS、sitemap、robots、canonical、Open Graph、Twitter Card 和 JSON-LD 都被保留。它们分别服务订阅、搜索引擎发现和外部分享，不要求读者注册，也不会改变正文阅读。

可访问性相关的结构同样保留：跳到正文、键盘焦点、明确的按钮标签、图片尺寸、减弱动画偏好和语义化页面区域。这些能力不像新组件那样显眼，却直接影响站点是否稳定可读。

它们有一个共同特点：价值来自长期一致，而不是一次视觉更新。因此最合适的维护方式不是靠发布前记忆，而是进入布局模板和自动审计。

## 保留：双部署，但只维护一份源码

项目同时支持 GitHub Pages 和 Vercel。前者使用 `/ryuho/` 子路径，后者使用站点根路径。

保留双部署并不意味着维护两套站点。两者共享文章、主题、脚本和审计，只在配置层覆盖 `url` 与 `root`。模板统一使用 Hexo 路径 helper，robots 与 manifest 根据当前配置生成。

发布前分别运行：

```bash
npm run check
npm run check:vercel
```

双部署的价值在于验证同一份静态源码可以适应不同托管路径，同时避免平台逻辑侵入文章和主题。只要差异仍然收敛在小范围配置内，这项能力值得保留。

## 保留：发布门禁和工程日志入口

`tools/audit-site.js` 会扫描关键产物、SEO、链接、图片、sitemap、文章元数据、脚手架和模板泄漏。它不能判断文章观点是否优秀，但能阻止缺少基础字段、目标不存在和构建结果不一致的提交。

`tools/daily.js` 则提供工程日志脚手架，默认包含目标、关键动作、验证结果和复盘。它把“记录一次改动”从空白页变成一组可回答的问题。

这两类工具被保留，是因为它们减少重复劳动，也把维护标准从个人记忆转成可执行流程。随着文章和页面增加，这种确定性比继续增加前台组件更重要。

## 删除：默认示例和空内容

审计脚本明确检查并阻止 `hello-world.md`、默认 Hexo 欢迎文案、空日记字段和启动占位内容。

这说明项目已经把“能证明模板工作”的示例，与“值得公开保留的内容”区分开。示例在初始化阶段有用，但长期留在线上会稀释站点定位，也可能进入归档、搜索和 RSS。

删除这类内容不只是清理页面。它同时改善了分类统计、搜索结果、站点地图和相关推荐候选。

## 替换：外部搜索依赖被本地索引取代

README 和审计规则都表明，当前搜索不再基于 Lunr.js，也不允许临时的 unpkg 或 jsDelivr 依赖进入生成页面。

替换并不是对成熟搜索库的否定，而是当前内容规模下的责任收缩。构建期索引已经能覆盖标题、摘要、标签、分类和正文检索；本地实现与站点一起发布，也能被双路径构建验证。

未来如果出现中文分词、索引体积或排序质量的明确需求，可以重新评估成熟方案。删除旧依赖的判断只对当前边界负责。

## 关闭：没有完整配置和场景的评论

主题保留了 Giscus 接入模板，但 `_config.yml` 中评论开关为关闭，仓库 ID 等字段也没有完整配置。审计还会阻止占位 ID 被输出到页面。

这是一种比“先放一个不可用评论区”更诚实的状态：代码具备未来接入点，但没有真实需求和完整配置时，不让它进入核心页面。

评论一旦启用，就要承担第三方脚本、身份体系、隐私、内容治理、主题适配和可用性责任。维护策略因此把没有真实场景的评论、社交和统计组件列为默认不做。

## 不再增加：纯装饰模块和空栏目

维护策略还明确排除了仅用于装饰的动画、卡片和视觉元素，以及没有内容承载计划的新栏目。

这不是说界面不能继续改善，而是要求改动服务阅读、导航、排版或移动端问题。一个模块如果只能回答“页面会更丰富”，却说不清读者任务，就不应自动进入待办。

同样，栏目必须由内容需求推动。先创建入口、以后再想写什么，会让首页和导航积累空壳；先形成一组有连续关系的文章，再建立专题，结构会更稳定。

## 判断保留与删除的标准

从当前仓库可以归纳出四条标准：

1. 是否服务公开内容的发现、阅读或订阅；
2. 是否符合静态架构和当前维护能力；
3. 是否能在两套部署配置中生成并验证；
4. 是否带来长期责任，却没有真实内容或使用场景。

满足前三条的搜索、专题、RSS、PWA 和审计被保留；触发第四条的空示例、临时外部依赖、未配置评论和纯装饰扩张则被删除、替换或保持关闭。

## 结论

维护一段时间后，这个博客保留的并不是“所有已经写过的功能”，而是一组围绕内容长期运行的能力：静态生成、本地主题、搜索、相关推荐、有限离线、订阅、双部署和质量门禁。

被删除或关闭的部分也有共同点：它们缺少真实内容、完整配置或明确场景，却会增加持续责任。

个人博客的成熟不一定表现为页面越来越满。能够说明每项能力为什么存在，也能在依据不足时主动不做，才是这个项目进入稳定维护阶段后最值得保留的东西。
