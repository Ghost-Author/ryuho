优化博客图片时，一个常被忽略的问题是：应该直接压缩源码图片，还是只压缩构建产物？

两种方式都能减少线上体积，但维护含义完全不同。

这个 Hexo 博客选择保留 `source/images` 中的原图，在静态页面生成完成后，再遍历 `public/images` 并压缩可获益的文件。源文件继续作为可重新处理的输入，发布目录则追求尽可能小的传输成本。

## 真实结果

当前站点有两张核心图片：

| 图片 | 源文件 | 构建产物 | 结果 |
| --- | ---: | ---: | --- |
| avatar.png | 2,124 bytes | 2,124 bytes | 跳过 |
| hero.jpg | 356,053 bytes | 55,933 bytes | 减少 300,120 bytes |

hero 是一张 1920×1080 JPEG。经过构建优化后，体积从约 348 KiB 降到约 55 KiB，减少约 84%。

头像只有 64×64、约 2.1 KiB，低于处理阈值，因此保持不变。

优化脚本每次构建都会打印实际处理文件数和节省体积。它不假设压缩一定有效，而是用产物数据回答。

## 为什么不直接改 source

直接覆盖源码图片看起来更省事，但会失去几个重要能力：

- 无法从原图重新选择编码参数。
- 多次有损压缩可能累积质量损失。
- Git 历史会混入与内容无关的二进制变化。
- GitHub Pages 和 Vercel 构建无法验证相同输入产生相同结果。
- 未来生成 WebP、AVIF 或响应式尺寸时缺少高质量来源。

保留原图意味着构建过程可以随时重跑。调整质量参数失败时，只需要修脚本，不需要从历史提交或其他位置找回素材。

这里的原则和编译类似：源码负责可维护性，构建产物负责交付效率。

## 为什么在 Hexo generate 之后运行

图片优化命令被放在静态站点生成之后：

```bash
hexo generate
npm run optimize:images
```

Hexo 会先把资源复制到 `public`，优化脚本只处理这个目录。

如果顺序反过来，Hexo 生成时可能再次用 source 文件覆盖优化结果。把优化作为构建后步骤，可以确保最终发布的正是压缩后的文件。

GitHub Pages 和 Vercel 两条构建命令都包含这一步，避免只有本地或某一个部署平台使用优化产物。

## 先设置最小处理阈值

脚本只处理大于 32 KiB 的 JPG、JPEG、PNG 和 WebP。

小文件通常没有足够压缩空间。启动 Sharp、解码、编码和写临时文件也有成本。跳过 2.1 KiB 的头像，既减少构建工作，也避免为了几十字节的收益增加不必要变化。

32 KiB 不是普适最佳值，只是当前站点的合理边界。图片数量和构建环境变化后，可以根据实际耗时调整。

## 不同格式使用不同策略

当前参数很克制：

- JPEG：质量 82、渐进式编码、mozjpeg。
- PNG：压缩级别 9、启用自适应过滤。
- WebP：质量 82。

脚本不会把所有图片统一转换成一种格式。

保留扩展名有两个现实好处。第一，模板和 Markdown 路径不需要变化；第二，manifest 等声明的 MIME 类型更容易保持一致。

格式转换可以进一步减少体积，但会带来 fallback、缓存键、引用路径和审计规则的额外复杂度。当前只有一张大图，重新编码原格式已经取得 84% 的收益，没有必要提前扩张管线。

## 为什么先写临时文件

Sharp 不会直接覆盖输入文件。脚本先把结果写到：

```text
<original path>.tmp
```

随后比较原文件和临时文件大小。

如果压缩后文件更小，就用临时文件替换原产物；如果结果相同或更大，就删除临时文件并保留原文件。

这个判断很重要。所谓“优化参数”并不保证所有图片都变小，尤其已经高度压缩的 PNG 或 WebP。以实际字节数作为替换条件，比相信编码器配置更可靠。

临时文件也避免编码失败时破坏已有产物。只有完整写入并确认有收益后，替换才发生。

## 为什么单个文件失败不会终止全部处理

遍历图片时，每个文件都有独立错误处理。某张损坏或不受支持的图片会输出 warning，其他图片仍然继续。

这是一项有意识的取舍。

图片优化属于构建增强，不应该因为一个可回退到原文件的编码问题让整个站点无法生成。但如果 `public` 目录不存在，脚本会直接失败，因为这说明构建顺序本身不正确。

换句话说：

- 环境或流程错误：失败并阻止发布。
- 单张图片无法优化：保留原图并给出警告。

不同故障采用不同严重级别，能让流程既严格又不过度脆弱。

## 压缩之外还检查什么

体积变小不代表图片链路完整。

站点审计还会检查：

- 页面中的图片是否声明 width 和 height。
- manifest 图标文件是否真实存在。
- 图标扩展名声明的 MIME 是否与文件签名一致。
- 所有图片 URL 在 GitHub Pages 与 Vercel 路径下是否可达。

width 和 height 能让浏览器在图片加载前预留布局空间，减少内容跳动。文件签名检查则能防止“扩展名写 PNG、内容实际是 JPEG”这种浏览器兼容和缓存问题。

性能优化应该覆盖传输、布局和正确性，而不只是压缩率。

## 目前没有做什么

当前管线没有生成：

- 多尺寸响应式图片
- `srcset`
- WebP/AVIF 多格式版本
- 模糊占位图
- 图片 CDN URL
- 自动裁剪或焦点识别

原因很简单：站点目前只有一张需要明显优化的大图。已有方案已经把它减少约 84%，继续增加图片管线的收益有限。

当文章开始大量使用照片、截图和架构图时，再考虑多尺寸和现代格式会更合理。

## 什么时候应该升级

出现以下信号时，当前方案就不够了：

- 页面开始包含多张 1,000 像素以上图片。
- 移动端仍然下载桌面尺寸素材。
- 图片成为 Largest Contentful Paint 的主要瓶颈。
- 仓库体积因原图快速增长。
- 同一素材需要卡片、正文和分享图多种尺寸。

那时可以在保留原图的前提下，由构建脚本生成派生资源，并让模板输出 `srcset` 和明确尺寸。

## 最后的判断

图片优化不是把质量参数调低一点，而是设计一条可重复、可回退、可验证的资产管线。

这个博客保留源码图片，只优化发布产物；先写临时文件，只在体积确实下降时替换；小文件跳过，单图失败可回退，流程错误则阻止构建。

它没有追求最先进的图片格式组合，但每一个决定都能从当前资源规模和真实数据解释。

对长期维护的个人项目来说，这比一次手工压缩更可靠，也比提前搭建复杂媒体平台更合适。
