谈到可观测性，人们通常想到服务端指标、分布式追踪和告警平台。一个没有数据库、没有常驻进程的静态博客，看起来似乎没有什么需要观察。

但静态只意味着运行时更简单，不意味着系统没有状态。源码、依赖、构建脚本、主题、生成产物、部署平台、缓存和外部配置共同决定最终页面。问题也不一定表现为服务器报错：错误链接、旧缓存、缺少搜索索引或错误 canonical 都可能在“站点还能打开”的情况下存在。

这个博客没有搭建完整监控系统，而是把可观测性收敛为三个问题：现在生成了什么、它是否符合发布契约、两种部署环境是否保持一致。

## 先定义静态站点需要看见什么

可观测性不是日志越多越好。对当前博客，真正有用的信号主要来自四个阶段。

### 内容输入

文章数量、front matter、正文长度和占位内容决定站点将要发布什么。这里的异常包括缺少 description、标签为空、封面未配置，或者只写了提纲就进入 `_posts`。

### 构建过程

Hexo 是否成功渲染，生成器是否输出搜索、SEO 和 Service Worker 文件，图片优化是否执行，依赖是否可以从锁文件安装，都属于构建状态。

### 静态产物

页面是否具有 canonical、description、分享元数据，链接与图片是否存在，Manifest 和 Sitemap 是否正确，是用户真正会接触到的发布结果。

### 部署差异

GitHub Pages 使用 `/ryuho/`，Vercel 使用 `/`。相同源码在两种 URL 模型下是否都成立，是单次默认构建看不见的状态。

这四类信号已经覆盖了博客维护中最确定的风险，不需要先引入通用监控平台。

## 构建日志是第一条时间线

`package.json` 把发布检查组织成固定命令：

```bash
npm run check
npm run check:vercel
```

第一条依次执行清理、GitHub Pages 构建、图片优化和站点审计；第二条使用 Vercel 配置重新清理和生成，再运行相同优化与审计。

这组日志提供一条很朴素的事件时间线：

```text
旧产物清理
-> Hexo 生成
-> 图片处理
-> 站点审计
-> 成功或失败
```

如果失败发生在生成阶段，优先检查模板、Markdown 或 Hexo 配置；发生在图片处理阶段，关注源文件与 Sharp；发生在审计阶段，则根据具体规则定位产物契约。

阶段清楚，比把所有命令塞进一个不透明脚本更容易判断问题位置。

## 审计输出应当同时提供状态与上下文

`tools/audit-site.js` 对每项规则输出 `PASS` 或 `FAIL`。失败时不仅设置非零退出码，还尽量附带 detail。

例如：

- 缺失的核心文件名；
- 元数据不完整的 Markdown 路径；
- 缺少 canonical 的 HTML；
- 断开的“来源页面 -> 目标 URL”；
- 类型不匹配的 Manifest 图标；
- 残留占位配置的页面。

状态用于让自动化决定是否继续发布，上下文用于让维护者快速修复。只有状态没有上下文，会迫使人重新运行大量命令；只有长日志没有明确状态，CI 又无法可靠阻断。

脚本结束时汇总检查数量和扫描到的 HTML 数量。这个数字不是业务指标，却能作为维护信号：文章与页面增加后，扫描范围应该随之增长；如果突然明显减少，可能是生成配置或内容路径发生了变化。

这里不应把页面数量包装成增长成绩，它只描述本次构建产物。

## 双环境构建是一种差异观测

单看 GitHub Pages 构建，写死 `/ryuho/` 的链接不会暴露；单看 Vercel，写死根路径也可能一直正常。

因此两套检查的价值不只是“多部署一个备份”，而是用两个真实环境检验同一个路径模型：

```text
同一源码 + 不同 url/root + 同一审计契约
```

如果一边通过、一边失败，差异范围已经被大幅缩小，通常集中在：

- 模板是否使用 `url_for` 或 `full_url_for`；
- robots、Manifest、Service Worker 是否按当前 root 生成；
- 搜索索引和结果链接是否依赖相对路径；
- canonical 是否重复拼接子路径。

这种对照比偶尔打开两个线上地址更可重复，也能在提交进入部署之前反馈。

## GitHub Actions 提供发布链路的可见状态

GitHub Pages 工作流从 `main` 检出源码，使用固定 Node 版本和 `npm ci` 安装依赖，运行 `npm run check`，只有成功后才把 `public` 发布到 `gh-pages`。

这条链路让一次发布至少具有以下可见状态：

- 哪个提交触发；
- 依赖是否按锁文件安装；
- 构建和审计是否通过；
- 发布步骤是否真正执行。

它没有收集浏览量，也没有声称线上页面一定在所有浏览器可用。CI 观察的是“可发布性”，不是“真实使用效果”。明确观察范围，才能避免把绿色构建误解为全部正常。

Vercel 连接的是 `main` 源码分支，而不是只包含产物的 `gh-pages`。生产分支本身也是可观测模型的一部分：看到 “No Output Directory named public” 时，需要先确认平台拿到的是不是包含 `package.json`、配置和源码的分支。

## 静态站运行时仍有盲区

目前这套机制主要覆盖构建期，不等于完整的线上监控。

它看不见：

- 真实网络下页面加载耗时；
- 某个地区能否访问外部评论脚本；
- Service Worker 已安装用户是否长期停留在旧缓存；
- 外部链接何时失效；
- 搜索词是否经常没有结果；
- 不同浏览器中的实际交互异常。

主题预留了 Plausible 分析配置，但只有配置 domain 时才加载脚本；评论也只在开关和 Giscus 配置有效时启用。当前仓库不能据此虚构访问数据或用户反馈。

如果以后确实需要补足运行时视角，应从明确问题出发：

- 需要了解内容发现，再考虑隐私友好的访问与入口统计；
- 需要发现前端异常，再引入受控的错误上报；
- 需要验证性能，再定期运行浏览器性能测试；
- 需要检查外链，再增加低频、可重试的链接任务。

没有使用决策的问题，不值得为了“看起来可观测”持续采集。

## Service Worker 为什么需要单独关注

离线能力让静态站多了一层状态：浏览器中的缓存可能和当前部署不同步。

当前 Service Worker 使用网络优先策略，核心路由和资源在安装时预缓存。构建审计可以确认 `sw.js` 存在、核心地址被写入、引用目标真实生成，却无法检查某个用户浏览器里正在控制页面的是哪个版本。

这正好说明构建可观测性和运行时可观测性的边界。前者证明“本次发布包含正确缓存清单”，后者才回答“客户端何时更新到这份清单”。在没有真实问题之前，项目选择保持策略简单，而不是引入复杂的版本上报。

## 让信号可以直接推动行动

一个维护信号只有在对应明确动作时才有价值。

| 信号 | 首要行动 |
| --- | --- |
| Hexo 生成失败 | 检查 Markdown、模板和配置 |
| 必需产物缺失 | 检查对应 generator 或页面源文件 |
| 内部链接失败 | 修正 URL helper、root 或目标页面 |
| 文章元数据失败 | 补齐 front matter 与正文 |
| 仅一套部署失败 | 比较 url/root 相关生成结果 |
| 图片类型失败 | 核对文件签名、扩展名和声明 |
| 页面扫描数异常下降 | 检查内容目录与生成配置 |

这张映射比增加一个复杂仪表盘更重要。观察不是为了收藏数据，而是为了缩短从异常到修复的路径。

## 如何验证可观测性本身

维护工具也会失效。审计脚本如果只输出成功，从未验证失败路径，就可能在规则写错后提供虚假信心。

新增检查时可以进行小范围故障注入：

- 临时移除一个必需文件，确认规则失败；
- 构造一个不存在的内部链接，确认 detail 包含来源和目标；
- 让 description 为空，确认源码审计阻断；
- 分别以 `/ryuho/` 和 `/` 生成，确认路径归一化结果一致。

验证后恢复临时改动，保持仓库干净。这种方式不需要搭建完整测试框架，却能证明关键观察信号真的会在异常发生时出现。

## 可复用的结论

个人博客需要的可观测性不必复制大型后端系统。可以从最小闭环开始：

1. 把内容、构建、产物和部署差异分成清楚阶段。
2. 为每个阶段保留稳定命令和明确退出码。
3. 失败信息同时输出状态、文件和原因。
4. 用所有真实部署配置重复验证同一契约。
5. 区分构建可发布性与线上真实体验。
6. 只采集能推动具体维护动作的信号。

静态站点的优势不是“永远不会出问题”，而是状态相对有限、许多关系可以在发布前被完整检查。把这些状态看见，就已经是一套与项目规模相称的可观测性。
