个人博客需要搜索吗？

文章只有几篇时，分类和归档已经够用。文章数量继续增长后，读者可能记得一个概念，却不记得它属于哪个专题。搜索的价值不是替代导航，而是提供一条按关键词回到内容的短路径。

这个博客曾经考虑过引入完整的前端搜索库，最后选择了更小的方案：Hexo 构建时生成 JSON 索引，浏览器加载后使用原生 JavaScript 匹配和排序，全程不依赖外部 CDN。

## 先明确搜索需要解决什么

站内搜索的目标很有限：

- 支持中文和英文关键词。
- 标题、标签、分类和正文都能命中。
- 标题命中应该排在正文偶然出现之前。
- 搜索结果能在 GitHub Pages 子路径和 Vercel 根路径正常跳转。
- 不把文章 HTML 直接插入页面。
- 不因为第三方 CDN 不可用导致搜索失效。

它不需要处理百万级文档，也不需要复杂的分词、同义词和拼写纠正。当前站点只有几十篇以内的内容，用大型搜索方案反而会增加维护面。

## 在构建期生成结构化索引

Hexo 已经掌握所有文章数据，所以最自然的索引时机是构建阶段。

生成器遍历按日期倒序排列的文章，提取：

- title
- content
- description 或自动摘要
- url
- date
- tags
- categories

正文会先移除 HTML 标签并合并空白，最终生成 `search-index.json`。

这样做有两个好处。第一，浏览器不需要再请求并解析所有文章页面；第二，搜索数据结构由构建过程统一控制，后续增加字段也不需要修改文章 HTML。

## 用简单权重表达搜索意图

浏览器拿到索引后，会把查询拆成以空白分隔的关键词，并对不同字段分别计分：

| 命中位置 | 权重 |
| --- | ---: |
| 标题 | 8 |
| 标签 | 5 |
| 分类 | 3 |
| 正文 | 1 |

这个权重没有复杂数学依据，它表达的是很直接的内容判断：

- 标题通常最能代表文章主题。
- 标签是作者主动标注的关键词。
- 分类比标签更宽泛。
- 正文命中只能证明文章提到过这个词。

每个关键词分别累计得分，最后按总分倒序排序，只展示前 12 条结果。

对小型博客来说，可解释的规则比难以调试的相关性算法更重要。发现结果不合理时，可以直接判断是哪一个字段的权重需要调整。

## 防抖和空状态也属于搜索体验

输入事件使用 300ms 防抖，避免用户每输入一个字符都重新扫描索引。

当查询为空时，结果区会清空；没有命中时，会明确显示“没有找到相关结果”。结果容器使用 `aria-live="polite"`，让辅助技术能感知搜索结果变化。

这些细节没有改变搜索算法，却决定了功能是否像一个完整产品，而不是一个技术 Demo。

## 为什么必须做 HTML 转义

搜索结果最终会拼接成 HTML。即使索引内容来自自己的 Markdown，也不能假设标题和摘要永远不包含特殊字符。

渲染前会对以下字符转义：

- `&`
- `<`
- `>`
- `"`
- `'`

这既能避免内容破坏页面结构，也保留了未来接入外部内容源时的安全边界。

更理想的实现可以完全使用 DOM API 创建节点，但在当前规模下，集中转义后再生成有限模板，仍然是可读且可控的方案。

## 相对路径解决双部署问题

GitHub Pages 使用 `/ryuho/` 子路径，Vercel 使用 `/` 根路径。搜索页如果写死任意一个前缀，另一套部署就会失效。

搜索页位于 `/search/`，因此索引使用：

```text
../search-index.json
```

文章结果也基于搜索页使用相对路径跳转。这让同一份页面在两种 root 下都能工作。

构建审计会分别运行 GitHub Pages 和 Vercel 配置，并检查搜索索引是否存在、搜索页是否使用相对路径、所有结果目标是否能在生成目录中找到。

## 为什么不依赖 CDN

搜索曾经可以通过 Lunr.js 或其他库快速完成，但外部 CDN 会带来额外故障点：

- 网络受限时脚本无法加载。
- CDN 地址或版本变化会影响历史页面。
- 隐私和安全策略需要放行第三方来源。
- service worker 无法完全保证离线可用。

当前原生实现的代价，是缺少成熟分词和高级查询能力。但在文章规模不大、关键词明确的技术博客里，这个代价可以接受。

项目审计现在会直接阻止 `unpkg` 和 `jsDelivr` 依赖重新进入生成页面。

## 什么时候应该升级

这套方案不是通用搜索引擎。出现以下信号时，才值得升级：

- 文章数量增长到浏览器全量扫描明显变慢。
- 中文分词质量成为真实问题。
- 需要拼写纠正、同义词或布尔查询。
- 搜索日志表明用户经常搜不到已有内容。
- 多种内容源需要统一索引。

在那之前，继续增加搜索复杂度只是提前支付维护成本。

## 最后的判断

一个功能是否“工程化”，不取决于使用了多强的库，而取决于它有没有明确边界、可解释规则、失败状态和回归验证。

这个搜索方案很小：一个构建生成器、一份 JSON 索引、一段浏览器脚本。但它服务了真实内容发现需求，同时适配双部署、离线缓存和质量审计。

对个人博客来说，这种刚好够用、容易理解、可以长期维护的方案，比一个功能更多但依赖更重的搜索框更合适。
