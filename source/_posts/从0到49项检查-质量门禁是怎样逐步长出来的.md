“这个项目有 49 项检查”听起来像一个结果，但数字本身没有多少意义。真正重要的是：为什么要检查这些事情，它们之间如何分层，以及新增规则时怎样避免把审计脚本变成一堆难以维护的断言。

需要先说明边界：本文依据的是本站当前 `tools/audit-site.js` 的实现和现有复盘，讨论这套规则所体现的演进逻辑。仓库没有为每一项检查保存一份逐次加入的完整叙事，因此这里不会声称“第几次提交增加了第几项”，也不会为数字编造时间线。

从工程上看，当前 49 项检查可以理解为从“有产物”到“敢发布”的五层质量问题。

## 背景：Hexo 只负责生成，不负责证明可发布

最初可用的判断往往只有一个：`hexo generate` 是否以成功状态退出。

这能证明模板大体可执行，却不能证明：

- 首页、搜索索引或专题页一定生成。
- 页面没有泄漏 `undefined` 或空模板文案。
- canonical、description 和分享元数据完整。
- 内部链接、图片与 sitemap 目标真实存在。
- GitHub Pages 子路径与 Vercel 根路径都正确。
- 文章源文件不是只有标题的提纲。

这些都是确定性问题，也都适合自动检查。质量门禁的价值，是把“构建完成”拆成一组可以失败、可以定位、可以重复验证的发布条件。

## 第一层：15 个必需产物先回答“有没有”

当前脚本把 15 个文件或页面列为必需产物，并逐项计入检查：

- 首页、404、RSS、sitemap、robots、manifest 和 service worker
- 专题总页、AI 工程专题、博客工程化专题
- 项目页、搜索页和搜索索引
- 主题 CSS 与 JavaScript

这一层最朴素，却是后续所有行为检查的前提。生成器没有加载、页面被误删、输出路径变化或构建流程漏掉资源时，错误会直接指向具体文件。

为什么每个文件单独算一项，而不是合并成“核心文件都存在”？因为失败输出需要可定位。审计的目标不是获得一个漂亮数字，而是让维护者看到 `required file: search-index.json` 就能立刻缩小问题范围。

## 第二层：入口与核心能力回答“能不能用”

文件存在不等于能力成立。首页可能没有项目入口，搜索页可能请求了错误索引路径，service worker 文件可能存在却没有预缓存核心路由。

因此当前脚本继续验证：

- 首页具备核心 SEO 标签，并链接 manifest、项目页和两条专题。
- 首页注册 service worker。
- 404 页面包含 `noindex, follow`。
- 搜索页用相对路径读取 `../search-index.json`。
- service worker 包含专题、项目、搜索索引、CSS 与 JavaScript 等核心预缓存目标。
- robots 包含 sitemap，且地址没有重复 `/ryuho/ryuho/`。
- manifest 具有名称、短名称、起始地址、图标和 maskable 图标。
- sitemap 至少包含一个 URL。

这些规则体现了门禁从“文件级”走向“行为契约”。它们没有启动浏览器模拟全部交互，而是检查当前实现中最关键、最容易发生回归的输出信号。

例如搜索采用相对索引路径，是为了同时适配 `/ryuho/search/` 和 `/search/`。审计检查的不是某个代码风格，而是双部署成立所依赖的约束。

## 第三层：源码与渲染结果回答“内容是否可发布”

静态博客的缺陷不只来自模板。文章可能缺少摘要、标签和分类，脚手架也可能不断生成空字段。

当前审计会解析 `source/_posts` 的 front matter，检查每篇文章至少包含：

- title 与 date
- 长度达到项目最低要求的 description
- 至少两个 tags
- 至少一个 category
- cover
- 去除代码和标签后不是过短的正文

它还检查 starter 文件名已经移除，scaffold 不会继续产生空 description、cover、tags 或 categories。这样规则不仅拦截当前坏内容，也约束未来内容的起点。

渲染结果方面，脚本扫描所有 HTML，阻止 `undefined`、`null`、默认 Hexo 欢迎语和空日记字段泄漏。文章页必须包含相关推荐，以及 `article:tag` 和 Twitter 分享图片。HTML 还不能引用临时 CDN 地址。

这些检查刻意只判断机器能确定的底线。它们不能判断观点是否新颖，也不能证明文章真的有 1800 字就一定值得阅读。内容洞察仍由作者负责，门禁只阻止明显不完整的页面上线。

## 第四层：全站一致性回答“承诺是否真实”

SEO 标签和链接最容易出现“字符串存在，但目标错误”的假通过。于是审计在遍历 `public` 时建立文件与目录集合，再检查全部 HTML。

当前全站检查包括：

- 非 404 页面都有 canonical。
- 所有页面都有 description。
- 非 404 页面都有 Open Graph URL。
- manifest 图标真实存在，声明类型与文件签名一致。
- HTML 图片声明 width 和 height。
- 首页“阅读最新文章”指向真实文章，而不是归档兜底。
- 站点具有工程实践与 AI 写作信号。
- 评论配置没有占位 ID。
- 所有内部链接和资源都能解析。
- sitemap 中列出的目标都存在。

这里的“一项检查”可能扫描很多页面。例如“html pages have canonical URLs”只计一项，但会汇总所有缺少 canonical 的文件。因此 49 不是页面数乘规则数，也不是测试用例执行次数，而是当前脚本最终汇报的 49 个发布条件。

这种计数方式让结果稳定且可读。文章增加后，HTML 扫描数量会增长，但规则总数不必跟着增长。

## 第五层：同一套规则验证两种部署

本站提供两条检查命令：

```bash
npm run check
npm run check:vercel
```

前者使用 GitHub Pages 的 `/ryuho/` root，后者合并 Vercel 配置并使用 `/`。两条流程都会清理、生成、优化图片，再执行同一个 `audit-site.js`。

这项设计比维护两份审计更重要。规则相同，配置不同，才能把路径差异暴露为可验证输入，而不是让两个环境逐渐拥有各自的例外。

审计内部会从 manifest 的 `start_url` 推导站点 base，再把 URL 转换成 `public` 相对路径。绝对站内地址、根路径地址和相对地址都经过统一解析。这样“内部链接可达”既能覆盖 Vercel，也能覆盖 GitHub Pages 子目录。

## 取舍：为什么不用完整测试框架

当前审计使用 Node.js 标准库、正则和文件系统遍历，没有引入浏览器测试框架或 HTML 解析依赖。

它的优势是依赖少、执行路径短、在本地与 CI 中容易运行。对确定性的静态产物检查，读取文件已经能够覆盖大部分风险。

代价也很明确：正则不能完整理解任意 HTML，脚本不会验证真实布局、键盘交互、网络缓存行为或搜索结果主观质量。当前项目通过人工浏览补充这些判断，而不是把所有问题都塞进一个脚本。

另一个取舍是只把稳定契约写成规则。一个临时页面文案、某篇文章的推荐顺序或首页某个装饰元素，不应轻易变成发布阻断项。门禁越严格，维护成本越高；只有当失败能够明确代表不可发布状态时，才值得加入。

## 验证与维护：数字增长不是目标

当前脚本最终输出每项 `PASS` 或 `FAIL`，失败时附上相关文件或路径，并在存在任意失败时用非零状态退出。CI 因此可以在部署前停止。

维护这套门禁时，更合理的问题不是“怎样从 49 增长到 60”，而是：

- 当前是否还有只能靠记忆完成的确定性检查？
- 某个真实回归是否能被稳定复现并低成本检测？
- 新规则是否同时适用于两套部署？
- 失败信息能否直接帮助定位？
- 规则是否会因无关内容变化频繁误报？

如果答案不明确，就不应为了数量增加断言。质量门禁的成熟表现不是项目永远添加检查，而是知道哪些风险值得自动阻断，哪些仍应交给人工判断。

## 结论

从 0 到 49 项检查，可以看作判断层次的变化：先确认构建产物存在，再确认核心入口可用；随后检查内容源和渲染结果，进一步验证全站链接、SEO 与资源一致性，最后让同一套契约在两种部署根路径下都成立。

本文没有为每条规则虚构提交历史。能够从当前实现确认的是，15 项检查对应必需产物，其余规则覆盖页面能力、内容质量和全站一致性，共同组成当前 49 项发布条件。

数字只是脚本输出。真正让项目变得可靠的，是每项检查都有明确风险、失败可定位、结果可重复，而且始终知道自动化的边界。
