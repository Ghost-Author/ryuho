个人项目复盘最容易写成两种东西：一种是功能清单，按顺序描述“我做了首页、搜索、部署”；另一种是结果宣传，用“性能大幅提升”“体验显著改善”概括一切，却没有证据说明提升发生在哪里。

可信的复盘不要求项目规模很大，也不要求一定经历严重事故。它只需要把事实、判断和边界分开：仓库里真正实现了什么，为什么在当时选择它，如何验证它有效，还有哪些事情没有做。

本站围绕自身工程化已经写了质量门禁、零 CDN 搜索、离线策略、图片管线、相关推荐和双部署等复盘。它们提供了一组可观察的写作样本，也暴露出个人项目写作最需要守住的原则：先找证据，再组织故事。

## 背景：个人项目最缺的不是故事，而是外部约束

团队项目通常有需求文档、工单、监控、用户反馈和上线记录。个人项目没有这些材料时，很容易用记忆补齐过程，把后来形成的认识写成一开始就有的设计，甚至为文章完整性虚构一次事故或用户评价。

这种写法读起来流畅，却削弱了复盘价值。读者无法判断哪些结论来自实现，哪些只是作者现在觉得合理。

个人项目真正可靠的资料通常就在仓库中：

- 配置文件说明运行环境和部署模型。
- package scripts 与 CI 文件说明实际发布链路。
- 主题模板说明页面行为。
- 生成器和工具脚本说明算法与失败策略。
- 构建产物和审计输出说明可以重复验证的结果。
- 现有文章与 README 说明项目已经公开过哪些判断。

复盘应当从这些材料建立事实表，而不是先想一个有戏剧性的标题。

## 判断一：把“事实”“解释”“结果”分开

以双部署复盘为例，可确认的事实是：主配置的 root 为 `/ryuho/`，Vercel 覆盖配置的 root 为 `/`；模板使用 `url_for` 与 `full_url_for`；robots 和 manifest 根据当前配置生成；两条检查命令最终运行同一个审计脚本。

基于这些事实，可以作出解释：项目把平台差异收敛到了 `url` 与 `root`，避免在模板中散落部署前缀。

可验证结果则是：使用两份配置分别构建时，内部链接、canonical、manifest、robots 和 sitemap 接受同一组检查。

三者不能混写成“这样设计后部署稳定性显著提升”，因为仓库没有提供稳定性百分比或长期故障统计。可信的表述应停在证据能够支持的位置。

同样，搜索复盘可以确认索引包含标题、正文、摘要、日期、标签与分类，排序权重是标题 8、标签 5、分类 3、正文 1，并且页面对输出做 HTML 转义。它不能据此声称搜索准确率达到某个比例，也不能假设读者更喜欢这个实现。

## 判断二：一篇复盘只回答一个核心问题

项目实现往往互相关联，但文章不能把所有工程决策一次说完。

本站的几篇复盘各自围绕一个可争论的问题展开：

- 质量门禁回答“Hexo 构建成功为什么还不够”。
- 搜索复盘回答“当前规模为什么选择构建期索引和零 CDN 依赖”。
- 离线策略回答“静态博客为什么采用 network-first，而不是缓存优先”。
- 图片复盘回答“优化应该修改源码，还是只处理构建产物”。
- 相关推荐回答“没有行为数据时，简单内容权重是否够用”。
- 双部署回答“同一份源码如何适配子路径和根路径”。

这些标题不是功能名，而是决策问题。正文因此可以围绕背景、候选方案、选择、实现、验证和边界展开。读者得到的不只是代码说明，还能看到这套选择在什么条件下成立。

如果一篇文章同时讲主题设计、SEO、搜索、PWA 和 CI，每部分只能停在清单。把问题收窄，反而能写清真正的取舍。

## 实践一：先制作证据清单

动笔前，可以用一个简单表格约束自己：

| 要写的判断 | 可引用证据 | 不能声称什么 |
| --- | --- | --- |
| 双部署共享源码 | 两份 Hexo 配置、URL helper、构建命令 | 高可用或零故障 |
| 搜索不依赖 CDN | 本地生成器、原生前端脚本、CDN 审计 | 用户满意度或搜索准确率 |
| 图片只优化产物 | `source/images`、`public/images`、Sharp 脚本 | 所有图片都能减少相同比例 |
| 推荐可解释 | 标签分类权重和排序代码 | 个性化或点击提升 |
| 门禁覆盖 49 项 | 当前审计脚本输出结构 | 不存在的逐次提交历史 |

这一步会主动暴露证据缺口。没有访问统计，就不要写“最受欢迎”；没有性能采样，就不要写“首屏提升 40%”；没有真实读者反馈，就不要用“用户普遍认为”增强说服力。

如果某个结果可以现场重现，应优先运行构建、审计或文件比较。如果只能从已有文章引用历史数值，要说明它是当时记录，而不是未经重新验证的当前状态。

## 实践二：写出判断过程，而不是只贴最终代码

好的复盘通常包含至少一个被放弃的合理方案。

图片优化文章没有简单说“使用 Sharp”，而是比较直接覆盖源码与只处理 `public` 的维护含义。最终选择保留高质量源文件，在 Hexo 生成后优化构建产物；先写临时文件，只有新文件更小时才替换；小文件跳过，单张处理失败则保留原图。

相关推荐文章也没有把几行排序包装成智能推荐。它先说明当前没有账号、行为数据和后端，只能做内容相关排序；然后解释共享标签加 2、共享分类加 1，同分按日期排序，没有主题交集时标记为“最近更新”。

取舍让文章具有迁移价值。读者未必使用 Hexo，但可以复用“保留可重新处理的输入”“能力命名不要超过实际边界”“先用现有元数据解决当前规模问题”等判断。

## 实践三：验证要与主张一一对应

“已经运行构建”不是所有问题的统一验证。

如果主张是双部署路径正确，就应分别使用两套配置构建，并检查链接、canonical、robots、manifest 和 sitemap。如果主张是搜索不依赖临时 CDN，就应检查生成索引、相对路径、输出转义，并扫描产物是否出现指定 CDN 地址。如果主张是文章元数据可供推荐与分享使用，就应检查 front matter、相关推荐区块和 `article:tag`。

本站审计读取 `public` 产物，同时读取文章源码与脚手架。这个组合很适合复盘写作：源码证明意图，产物证明实际输出。只读代码可能忽略模板渲染结果，只看页面又无法解释生成逻辑。

验证段落还应报告失败边界。例如自动审计能够证明相关推荐区块存在、链接可达，却不能证明前三篇是最符合读者意图的结果。明确“验证了什么”和“没有验证什么”，比笼统写“测试通过”更可信。

## 取舍：允许项目保持简单，也允许文章承认未完成

复盘常见的另一个问题，是为了显得完整而补出一套未来架构。

当前图片管线没有 `srcset`、AVIF、多尺寸派生图和图片 CDN；搜索没有中文分词、模糊匹配或服务端索引；推荐没有向量语义和用户行为；评论配置默认关闭；专题仍是手工 Markdown 页面。

这些“没有做”不是缺陷清单，而是当前规模下的边界。文章应解释为什么暂不做，以及出现什么信号后值得升级。这样读者能够判断方案适用范围，作者也不会把路线图误写成已交付能力。

个人项目尤其需要这种克制。没有团队替未来抽象付维护成本时，简单方案往往是有意识的工程选择，而不是能力不足。

## 验证：如何审查一篇复盘是否可信

发布前可以反向检查每一段：

- 数字能否由脚本、文件或明确记录重现？
- “实际”“当前”“已经”后面的内容在仓库里是否存在？
- 是否把推断写成了事实？
- 是否引用了没有收集过的用户反馈、事故或线上指标？
- 实现细节是否与当前代码一致？
- 结论是否写明适用规模与未覆盖范围？
- 文章是否给出验证方法，而不只是宣布成功？

本站还通过构建门禁检查文章 title、date、description、tags、category、cover 和正文最低完整性。它能防止空提纲发布，却不能替代上面的事实审查。机器检查格式，人检查证据与措辞。

## 结论

可信的个人项目复盘，不靠项目规模，也不靠把过程写得惊险。它依赖一条朴素链路：从配置、代码、脚本和产物建立事实；围绕一个明确问题说明判断；展示选择与放弃；用与主张匹配的方法验证；最后坦率写出边界。

本站已有复盘之所以能够形成连续内容，不是因为博客功能复杂，而是每篇都尝试回答一个真实工程问题。双部署、搜索、图片、推荐和质量门禁都能在仓库里找到对应实现，也都保留了“当前为什么够用、什么时候需要升级”的条件。

写作不是给项目补一层漂亮叙事，而是把可验证的工程判断整理出来。证据能够支持到哪里，结论就写到哪里。这种克制，正是个人项目复盘最可靠的说服力。
