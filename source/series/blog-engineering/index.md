这个专题记录 Ryuho 博客自身的工程化过程。

它不是一套“最佳 Hexo 配置”，而是一条真实演进路径：先让站点定位清楚，再整理阅读体验，随后补搜索、专题、部署和质量检查，最后主动停止没有需求支撑的功能扩张。

## 阅读路径

### 1. 先明确为什么要维护

个人博客值得长期维护的前提，不是页面足够漂亮，而是它能持续沉淀技术判断、项目经验和写作成果。

关联阅读：{% post_link 小站开张-把个人博客当作长期工程 '小站开张：把个人博客当作长期工程' %}

### 2. 整理信息架构

首页、分类、标签和关于页承担不同责任。先让读者知道站点关注什么，再考虑更多视觉细节。

关联阅读：{% post_link 日记-2026-02-07 '站点整理日志：先把信息架构理顺' %}

### 3. 让主题服务阅读

卡片、时间线、深色模式和阅读状态都只是工具。它们的共同目标，是降低浏览和连续阅读成本。

关联阅读：{% post_link 日记-2026-02-08 '站点整理日志：让主题服务阅读体验' %}

### 4. 把博客当作工程项目

当内容和页面增多后，构建、部署、SEO、搜索和内容质量需要进入同一条维护流程。

关联阅读：{% post_link 把个人博客当作工程项目维护 '把个人博客当作工程项目维护' %}

### 5. 建立发布门禁

最终的质量基线不是“Hexo 没报错”，而是关键页面、链接、资源、元数据、内容和两套部署配置都经过自动验证。

关联阅读：{% post_link 从能构建到敢发布-为Hexo博客建立质量门禁 '从能构建到敢发布：为 Hexo 博客建立质量门禁' %}

### 6. 用最小依赖解决内容搜索

站内搜索不一定需要大型前端库。构建期索引、简单权重、输出转义和双路径验证，足以覆盖当前内容规模。

关联阅读：{% post_link 静态博客搜索为什么选择零CDN依赖 '静态博客搜索为什么选择零 CDN 依赖' %}

### 7. 为静态站增加有限的离线韧性

service worker 采用核心资源预缓存和 network-first 策略，优先保持内容新鲜，在网络失败时回退到已缓存页面。

关联阅读：{% post_link 个人静态站的离线策略-为什么选择网络优先 '个人静态站的离线策略：为什么选择网络优先' %}

### 8. 把图片压缩变成可回退的构建步骤

保留高质量源码，只优化 public 产物；先写临时文件，只在体积确实下降时替换，并用审计检查尺寸和真实格式。

关联阅读：{% post_link 图片优化应该发生在源码还是构建产物 '图片优化应该发生在源码还是构建产物' %}

### 9. 用内容元数据生成相关推荐

共享标签每个加 2 分，共享分类加 1 分，同分时优先较新文章；没有主题交集时，诚实退化为最近更新。

关联阅读：{% post_link 零后端的相关文章推荐-简单权重够不够 '零后端的相关文章推荐：简单权重够不够' %}

### 10. 让同一份源码适配两种部署根路径

GitHub Pages 使用 `/ryuho/`，Vercel 使用 `/`。部署差异只保留在 url 与 root，其余路径由 helper、生成器和同一套审计处理。

关联阅读：{% post_link 同一套Hexo源码如何同时部署到GitHub-Pages和Vercel '同一套 Hexo 源码如何同时部署到 GitHub Pages 和 Vercel' %}
