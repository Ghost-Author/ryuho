个人博客的内容生产流程也值得工程化

2026-07-28 6 分钟阅读 2660 字
工程实践 技术写作 Hexo 内容工程
查看归档

个人博客的写作流程通常很随意：新建一个 Markdown，写完正文，运行构建，然后推送。文章不多时，这种方式几乎没有成本；内容逐渐形成系列后，遗漏描述、标签失控、日期格式不一致、草稿直接发布等小问题会开始反复出现。

工程化内容生产并不意味着给写作套上复杂审批。这个博客采用的方案很轻：用脚手架提供结构，用 tools/daily.js 降低创建成本，用审计器守住最低元数据，再由两套构建验证最终产物。自动化负责消除重复劳动，选题和判断仍然留给作者。

先区分创作问题与流程问题

文章是否值得写，是创作问题。文件放在哪里、元数据是否完整、页面能否被搜索和分享，则是流程问题。

这两类问题混在一起时，写作者很容易在动笔前消耗注意力：

  • 文件名应该怎么处理空格和标点？
  • 日期要写到哪一秒？
  • tags 与 categories 用什么格式？
  • description 是摘要还是开场白？
  • 封面是否需要每次重复填写？
  • 写完后要运行哪一组命令？

这些都不需要每次重新思考。适合工程化的部分，正是那些答案稳定、容易遗漏、又能被程序验证的动作。

脚手架定义文章的最低结构

仓库中的 scaffolds/post.md 没有尝试生成一篇“像写完了”的文章，而是提供统一 front matter 和五个问题：

这个结构适合工程文章，因为它迫使记录不止停在“我做了什么”。背景解释为什么要做，方案和实现区分判断与动作，验证说明如何确认结果，复盘再提炼可迁移经验。

脚手架同时预置：

  • title 与 date；
  • 两个基础标签；
  • 工程实践分类；
  • description 的写法提示；
  • /images/hero.jpg 默认封面。

默认值的意义不是让所有文章长得一样，而是保证新文件从第一分钟就接近可发布状态。真正需要作者填写的，是标题、具体描述、主题标签和正文内容。

文件名通过 slugify 处理：去除首尾空白、转成小写、把空格换成连字符、保留中文与 ASCII 字母数字，并折叠重复连字符。日期与时间则由统一函数补齐两位数字。

脚本还做了两个看似普通但重要的判断：

  1. _posts 不存在时才创建目录。
  2. 同名文件已经存在时直接失败，不覆盖旧内容。

这使日更命令保持幂等边界：它可以帮助开始一篇记录，却不会以“方便”为由替作者改写已经存在的文章。

生成内容仍然只是骨架，包含今日目标、关键动作、验证结果和复盘。它没有自动填充虚构结论，也没有把 Git 提交记录拼成貌似完整的日报。对技术写作来说，宁可留下明确待写项，也不能用自动生成掩盖事实缺口。

元数据不是装饰，而是多处功能的输入

在 Hexo 中，front matter 会同时进入多个消费端。

title 用于文章页、首页、归档、搜索和分享标题；description 会进入列表摘要、搜索结果和 meta description；tags 与 categories 支撑导航、相关推荐、关键词和内容组织；cover 用于文章头图、Open Graph 与 Twitter 分享图片；date 决定排序、链接和订阅源时间。

因此“正文写完了”并不等于内容已经完整。缺少 description 的文章，模板只能从正文截取；没有标签的文章不仅难以浏览，也会让相关文章算法失去判断信号。

审计器会直接读取 source/_posts/*.md 的 front matter，并检查：

  • 标题与日期存在；
  • description 长度至少达到最低要求；
  • 至少两个标签；
  • 至少一个分类；
  • 封面存在；
  • 去除代码块、HTML 与空白后，正文不是过短的提纲。

这里检查的是结构完整性，不评价表达水平。它能阻止明显半成品，却不能替代作者通读。

描述字段应当独立写，而不是机械截断

模板和搜索索引都提供摘要回退：没有 description 时，从正文去标签后截取一段文字。这保证页面不会完全空白，但不是理想生产方式。

正文开头往往承担铺垫，不一定准确概括文章价值。description 更适合回答三个问题：

  • 文章处理什么具体问题？
  • 使用什么视角或实现？
  • 读者最终能带走什么？

独立填写后，同一段描述可以稳定服务首页列表、搜索结果、SEO 和社交分享，不必依赖每个消费端各自猜测摘要。

这一步还解决了一个常见误区：只检查本次文章文件。新文章会改变首页最新文章入口、文章总数、分页、RSS、Sitemap、搜索索引和相关推荐，因此验证对象必须是整个站点产物。

为什么没有自动完成所有写作步骤

当前流程没有自动选题、自动分类，也没有在创建文件时调用语言模型生成正文。这是有意保留的边界。

自动化程度越高，越需要回答事实来源和审核责任。这个博客的工程复盘必须以仓库真实实现为依据，不应虚构访问量、用户反馈或线上事故。让脚本负责格式，让作者负责证据，是更清楚的职责划分。

同样，标签也没有完全自动推断。程序可以从关键词猜测，但“这篇文章属于哪个知识路径”是内容判断，错误分类带来的长期噪声比少敲几个字更难清理。

一条足够轻的生产流水线

结合当前实现，一篇工程文章的完整流程可以归纳为：

  1. 从真实改动或明确问题中确定选题。
  2. 使用 Hexo 脚手架或日更命令创建文件。
  3. 补全 description、主题标签和文章结构。
  4. 对照代码、配置和构建结果核对事实。
  5. 运行源码元数据与构建产物审计。
  6. 分别验证子路径和根路径部署。
  7. 查看 Git diff，确认没有夹带无关文件后再提交。

这条流程没有内容管理后台，也不需要外部服务，但已经把创建、约束、生成、验证和发布串了起来。

可复用的结论

内容工程化的目标不是提高“日产量”，而是让作者把注意力留给真正需要判断的部分。

稳定格式交给脚手架，重复命名交给命令，结构底线交给审计，跨环境结果交给构建。机器不替作者思考，却能让每次写作少处理几件机械小事，也让一篇文章从 Markdown 进入整个内容系统时更可预测。

对于个人博客，这已经足够形成一条长期可维护的生产流程：轻量、透明，并且不会为了自动化而牺牲内容可信度。
