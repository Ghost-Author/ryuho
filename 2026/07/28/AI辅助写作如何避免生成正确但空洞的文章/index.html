AI 辅助写作如何避免生成“正确但空洞”的文章

2026-07-28 7 分钟阅读 3161 字
工程实践 AI 辅助写作 技术写作 内容质量
查看归档

AI 很擅长生成一篇“看起来像技术文章”的文本：先描述行业背景，再列出几条最佳实践，补一段代码，最后总结要重视可维护性。每句话单独看都可能正确，整篇却没有提供新的判断，也无法证明它和正在讨论的项目有什么关系。

这类文章的问题不是语法错误，而是缺少对象。把 Hexo 换成任意框架，把博客换成任意网站，正文仍然成立。它读起来完整，却没有真实约束、实现细节和验证结果，因此很难成为可信的项目复盘。

这批博客工程化文章采用了另一种流程：先读取仓库，把可验证事实整理成证据表，再确定每篇文章能说什么、不能说什么，最后让构建审计检查文章是否达到最低发布标准。AI 负责组织和表达，但不拥有虚构事实的权限。

“正确但空洞”通常如何产生

最常见的原因，是写作从标题直接跳到了正文。

例如要写“静态博客如何产品化”，模型很容易列出搜索、评论、统计、推荐和 PWA。但当前仓库并没有启用评论，没有统计系统，也没有服务端用户数据。如果只凭主题联想展开，这些通用能力会被误写成项目已经完成的事实。

另一种空洞来自不受约束的叙事。为了让文章更有故事性，文本可能自动出现“上线后用户明显增加”“曾经发生生产事故”“维护半年后数据证明”等句子。它们符合复盘文章的常见结构，却没有任何仓库记录支撑。

还有一种问题更隐蔽：事实都是真的，但只做了功能罗列。search-index.json、service worker、canonical 和审计脚本被依次介绍，却没有解释它们解决什么问题、为什么选择当前实现、在哪些情况下不适用。

避免空洞，需要同时约束事实、结构和结论。

第一步：先建立证据表

证据表不是正式文档，也不一定要使用复杂工具。它可以是写作前的一组记录，每条包含“事实、来源、允许的结论、禁止外推”。

以这个仓库为例，证据可以整理成：

事实 仓库来源 可以写出的结论 不能外推
构建期生成搜索索引 scripts/search-index.js 搜索不需要在线 API 或 CDN 搜索质量优于专业引擎
service worker 使用 network-first scripts/service-worker.js 网络失败时可回退到缓存 全部文章一定离线可用
评论配置默认关闭 _config.yml 项目主动收紧无场景功能 读者不需要评论
两套命令运行同一审计 package.json 双部署共享质量基线 两个平台从未出现线上问题
维护策略排除空栏目 MAINTENANCE.md 新功能必须有内容承载 所有删除都来自用户数据

这张表最重要的一列是“不能外推”。AI 辅助写作的问题往往不是不会找事实，而是会从一个事实自然补全成更戏剧化的故事。

如果仓库只能证明“实现了审计”，文章就写规则、实现和验证方式；不能顺势写成“审计已经避免了多次线上事故”。如果只能证明“维护了一段时间”，标题就不使用无法核实的“半年后”。

第二步：把题目改写成可回答的问题

宽泛题目很容易得到宽泛答案。

“没有后端还能做什么”可以改成：

  • 哪些数据能在 Hexo 构建期确定？
  • 哪些状态可以只留在浏览器？
  • 哪些能力必须依赖可信服务端？
  • 当前仓库分别实现到了哪里？

“为什么不用成熟主题”可以改成：

  • 本地主题承担了哪些产品责任？
  • 哪些需求与当前内容结构紧密绑定？
  • 本地维护增加了什么成本？
  • 什么情况下成熟主题反而更合适？

问题一旦具体，文章就不需要靠宏大观点填充篇幅。每个段落都在回答一个可核对的问题。

第三步：为每篇文章设定事实边界

这批文章在写作前有几条明确约束：

  • 基于 README、主题、scripts、tools 和现有专题；
  • 不虚构用户规模、事故、半年统计或个人经历；
  • 成熟主题不是被批评对象，讨论的是需求匹配和控制权；
  • 原题缺乏时间证据时，主动改成可验证表述；
  • 每篇都要有背景、边界、方法、取舍、验证和结论。

这些约束比“请写得专业一些”有效得多。后者只改变语气，前者决定信息是否合法。

对 AI 来说，负面约束尤其重要。告诉它“结合真实项目”仍可能让它补出合理细节；明确列出“不能写用户量、线上事故和半年结果”，才把高风险叙事排除在生成空间之外。

第四步：从实现细节中提炼观点

事实不是文章，代码清单也不是文章。技术写作需要在实现和判断之间建立连接。

例如，scripts/search-index.js 会把文章标题、正文、摘要、标签和分类写入 JSON。这一事实可以支持三个层次：

  1. 实现层：搜索索引在构建期生成；
  2. 取舍层：当前规模下选择本地简单检索，避免外部依赖；
  3. 边界层：它不具备服务端搜索分析和复杂语义能力。

再如，图片优化只处理 public。这不只是一个命令细节，它体现了“源码保真、产物优化、失败可回退”的工程判断。

高质量文章的观点不是先写好再找代码装饰，而是从多个实现细节中归纳出一致原则。这样得出的结论范围更小，却更可信。

第五步：强制写出取舍和反例

“我们选择了本地实现，因为更轻量”仍然可能是一句空话。需要继续回答：轻量体现在哪里，失去了什么，何时应该更换方案？

关于成熟主题，文章必须同时承认它的社区验证、文档和升级优势；关于静态搜索，必须说明索引体积和语义能力边界；关于 PWA，必须区分有限缓存回退与完整离线应用；关于审计，必须承认机器无法判断文章是否有洞察。

反例能防止 AI 把每项当前选择包装成“最佳实践”。真实工程通常只有在当前约束下更合适的方案，没有脱离上下文的唯一答案。

一个实用检查是：如果文章里所有方案都只有优点，没有迁移条件和失败方式，它大概率仍然是一篇宣传稿。

第六步：让验证进入文章，而不是停在代码

技术文章中的“验证”不应该只写“运行后效果良好”。

这个项目有两个明确入口：

它们分别生成 GitHub Pages 子路径和 Vercel 根路径产物，然后运行同一审计。审计检查关键文件、元数据、内部链接、图片尺寸、sitemap、相关推荐、文章源文件和模板泄漏。

因此文章可以准确描述“如何确认改动满足发布底线”，而不需要虚构线上指标。

对内容本身，也可以增加结构化验证：

  • front matter 是否包含完整字段；
  • description 是否说明问题和读者收益；
  • 标签和分类是否来自现有信息架构；
  • 正文是否包含事实来源、边界和取舍；
  • 是否出现仓库无法证明的数字和经历；
  • 命令、文件名和配置是否真实存在。

构建审计负责可机器判断的部分，事实复核负责语义真实性。两者不能互相替代。

第七步：对生成稿做“去模板化”复核

初稿完成后，可以逐段询问：

  1. 这一段是否只能出现在这个项目里？
  2. 它引用了哪条仓库事实？
  3. 它新增了判断，还是重复标题？
  4. 删除后是否影响论证？
  5. 是否把可能性写成了已发生事实？

“在当今快速发展的技术环境中”“随着用户规模增长”“显著提升体验”这类句子通常需要特别检查。它们未必错误，但如果没有具体对象和证据，往往只是连接段落的填充物。

还要检查数字。审计项数量、页面数量和压缩体积会随着仓库变化，如果文章使用某次构建数字，就应确认它是否仍然准确，或者改写成不依赖瞬时统计的描述。

AI 在这个流程里最适合做什么

AI 的优势仍然很明显：

  • 快速阅读多个文件并聚合相关证据；
  • 把同一事实组织成不同文章角度；
  • 检查结构是否缺少边界或验证；
  • 发现前后术语不一致；
  • 将代码实现转译成读者可理解的语言；
  • 在明确约束下完成较长初稿。

但选题是否值得写、哪些事实可以公开、结论是否符合真实经历，仍然需要项目拥有者负责。AI 可以扩大表达能力，不能替代事实所有权。

结论

避免“正确但空洞”，不是要求 AI 写得更像人，而是改变写作输入和验收方式。

先读仓库，再建立证据表；先写事实边界，再生成正文；从实现提炼判断，同时保留反例和迁移条件；最后用构建审计与人工事实复核共同验收。

当每个重要结论都能回答“依据在哪、边界在哪、如何验证”，AI 辅助写作才不只是快速生产通顺文本，而是在帮助项目形成可追溯、可维护的技术记录。
