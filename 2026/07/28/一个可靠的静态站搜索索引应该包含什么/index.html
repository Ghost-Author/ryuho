一个可靠的静态站搜索索引应该包含什么

2026-07-28 8 分钟阅读 3536 字
工程实践 Hexo 搜索 数据设计
查看归档

静态博客的站内搜索通常由两部分组成：构建阶段生成索引，浏览器加载索引并完成匹配。界面和排序规则容易被看见，但真正决定搜索是否可靠的，是两者之间那份 JSON 数据。

这个博客的 scripts/search-index.js 很短。它遍历 Hexo 文章，提取标题、正文、摘要、路径、日期、标签和分类，最终生成 search-index.json。代码简单并不意味着数据可以随意设计；恰恰因为没有后端兜底，索引文件本身就是稳定的数据契约。

本文只讨论索引的字段和边界，不再重复为什么选择浏览器原生搜索或零 CDN 依赖。

先从消费者需要什么反推字段

当前搜索页需要完成三件事：

  1. 判断查询词是否命中标题、标签、分类或正文。
  2. 根据命中字段计算相关性分数。
  3. 展示标题、摘要、日期和文章链接。

浏览器因此不需要了解 Hexo 数据类型，只处理普通 JSON。

id 用于身份，url 用于导航

id 和 url 看起来都能标识一篇文章，但职责不同。

id 来自 post._id，表达索引内部的文档身份。当前前端还没有用它做去重或缓存更新，但保留这个字段为后续增量处理提供了稳定位置。

url 使用 post.path，表达文章在站点中的相对位置。它故意不生成带域名的绝对地址，因为同一份源码要部署到 GitHub Pages 子路径和 Vercel 根路径。搜索页位于 /search/，结果通过 ../${doc.url} 解析，索引不绑定任何一个生产域名。

这说明身份与位置不应混为一谈。以后 permalink 变化时，导航地址可能改变，但不必因此把所有消费逻辑都改成依赖 URL 作为主键。

title 是展示字段，也是最高价值的检索字段

title 既用于结果标题，也承担最高权重匹配。生成器对缺失标题回退为空字符串，防止序列化时报错；但源码审计会在更早阶段阻止无标题文章发布。

这种“双层防御”值得保留：

  • 生成器保证面对异常数据时仍能产生结构合法的 JSON；
  • 审计器保证生产内容不依赖这种回退长期运行。

如果只在生成器里直接抛错，失败上下文可能不如统一元数据审计清楚；如果只静默回退，搜索结果则可能出现无法辨认的空标题。

excerpt 必须有清楚的来源优先级

搜索结果不适合展示完整正文，所以生成器先从清洗后的 content 截取 200 个字符，正文更长时追加省略号。真正写入 excerpt 时，优先采用 post.description：

这个顺序把人工判断放在自动回退之前。description 通常能更准确地说明问题、方案和文章价值，自动摘要只负责保证旧文章或异常内容仍有可展示文本。

消费者端仍保留最后一层回退：如果 excerpt 为空，就从 content 截取 150 个字符。这形成三个层级：

  1. 作者编写的 description；
  2. 构建期生成的 200 字摘要；
  3. 浏览器端临时截取。

正常文章应停在第一层，后两层只用于容错。多个回退必须使用相同语义，否则不同页面可能展示完全不同的“摘要”。

tags 与 categories 应保留数组语义

把标签拼成一个长字符串也能搜索，但数组更适合作为数据契约。

数组可以明确区分两个标签，消费者需要展示标签、计算交集或调整单个标签权重时不必重新拆分字符串。分类同理，即使当前文章通常只有一个分类，也不应在索引层提前假设它永远是单值。

date 为什么使用展示友好的稳定格式

搜索结果只显示日期，不进行复杂时区计算，因此索引输出 YYYY-MM-DD，而不是序列化完整日期对象。

这样可以避免浏览器因时区转换把文章显示到前一天，也减少无用字节。代价是失去了时分秒信息，不能直接用于同一天多篇文章的精确排序。

当前生成器已经按 -date 遍历文章，JSON 顺序天然是倒序；前端排序只按匹配分数，没有用日期打破同分。若未来需要确定的二级排序，契约应增加完整时间戳或显式排序字段，而不是从简化日期中猜测。

前端使用稳定排序实现时，同分文档通常会保留这一顺序，但不应把这种语言实现细节当成长期保证。更可靠的方式是在搜索排序中明确加入日期二级比较，或者在契约文档中声明 documents 已按时间倒序。

这也是索引设计的重要经验：隐含规则同样会被消费者依赖。发现它时，应当选择“正式声明”或“明确消除”，不能长期保持模糊。

体积与召回率之间如何取舍

当前索引保存每篇文章的完整纯文本，因此正文中的任意关键词都有机会命中。代价是文章越多，JSON 越大，浏览器首次搜索前要下载和解析更多内容。

可以减少体积的方法包括：

  • 只保留标题、描述、标签和分类；
  • 限制正文长度；
  • 在构建期生成词项表；
  • 对内容做分片或按分类加载。

但每种优化都会降低召回率或增加实现复杂度。当前站点文章规模较小，全量正文索引仍然清楚可控。是否升级不应由“索引看起来不够高级”决定，而应根据实际文件体积、加载时间和查询效果判断。

如何验证索引契约

现有审计首先确认 search-index.json 必须生成，搜索页必须通过相对路径加载它，所有站内资源也需要在两种 root 下可达。

更针对数据契约的验证可以继续保持轻量：

  • 顶层必须包含 documents 数组；
  • 每条文档都具有固定字段和正确类型；
  • url 不得包含生产域名或开头错误的部署前缀；
  • title、excerpt 不得为空；
  • tags、categories 必须始终为数组；
  • 文档数量应与可发布文章数量一致；
  • JSON 中不能混入 HTML 标签或 undefined。

这些规则验证的是生产者与消费者能否继续协作，不评价某个关键词排名是否“足够聪明”。排序质量应该使用独立查询样例测试。

可复用的结论

静态搜索索引不是构建过程顺手导出的一份缓存，而是一个面向浏览器消费者的公开数据结构。

设计时应当明确：

  1. 每个字段由谁生产、由谁消费。
  2. 身份、导航、检索和展示字段分别承担什么职责。
  3. 人工描述与自动摘要采用怎样的回退顺序。
  4. 哪些结构必须保留数组或日期语义。
  5. URL 是否独立于域名和部署 root。
  6. 顺序、空值和异常内容如何处理。
  7. 何时为了体积牺牲正文召回率。

可靠不等于字段很多，而是每个字段都有明确语义，缺失时有可预期行为，演进时也知道会影响哪些消费者。
