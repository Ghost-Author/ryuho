静态站点的 SEO，不只是加几个 meta 标签

2026-07-28 7 分钟阅读 3264 字
工程实践 Hexo SEO 静态站点
查看归档

静态站点做 SEO，最常见的起点是在 <head> 中加入 description、keywords 和 Open Graph。它们确实重要，但只解决了“页面怎样描述自己”的一部分问题。

一个页面能否被稳定发现，还取决于 URL 是否唯一、内部链接是否可达、sitemap 是否指向真实页面、robots 是否给出正确地址、文章是否有可分享图片、404 是否避免进入索引，以及这些结果在 GitHub Pages 子路径和 Vercel 根路径下是否一致。

本站没有把 SEO 当成一次模板装修，而是把它拆成内容元数据、页面语义、站点发现、路径生成和产物验证五个层面。

背景：构建成功不代表搜索引擎看到的是正确页面

Hexo 能生成 HTML，并不意味着输出自动具备稳定的搜索语义。

文章缺少 description 时，搜索引擎只能从正文自行截取；canonical 拼错时，同一内容可能出现多个地址；robots.txt 中 sitemap 路径重复了 /ryuho/，文件仍然存在，但入口无效；图片没有绝对地址，社交分享卡片可能无法读取；404 页面如果没有 noindex，错误页也可能被收录。

这些问题不会阻止浏览器显示正文，也通常不会让 hexo generate 失败。它们只能在生成后的页面和文件中被看见。

因此，SEO 的工程目标不是“拥有多少标签”，而是让每篇可发布内容都有一致、可解释且可验证的公开身份。

判断一：元数据先来自内容，而不是模板猜测

本站要求文章 front matter 包含 title、date、description、tags、categories 和 cover。模板会优先使用这些显式字段，再提供有限回退：

  • 页面标题由文章标题和站点标题组合。
  • description 优先使用页面 description，否则从摘要或正文去除 HTML 后生成。
  • 最终 description 会合并空白并截取到 160 个字符。
  • keywords 由标签、分类和站点关注方向去重组合。
  • 分享图片优先使用文章 cover，再回退到主题的默认图片或头像。

回退机制保证普通页面不会因为少量字段缺失而渲染异常，但文章发布仍由源码审计要求显式 description。原因是作者写出的摘要通常比模板截取正文更准确，也能避免代码片段、开场铺垫或目录成为搜索摘要。

本站审计将 description 少于 24 个字符视为薄弱元数据。这不是搜索引擎规则，而是项目自己的最低发布约束：摘要至少应能说明文章解决什么问题。

判断二：一个页面需要唯一且适配环境的 URL

模板为除 404 外的页面输出 canonical，并同时写入 og:url 和结构化数据中的 url。文章若有 permalink 则使用 permalink，否则通过 Hexo 的 full_url_for 生成绝对地址，并移除末尾的 index.html。

真正需要注意的是本站有两种部署路径：

  • GitHub Pages 位于 https://ghost-author.github.io/ryuho，root 是 /ryuho/。
  • Vercel 位于站点根路径，root 是 /。

如果在模板里写死 /ryuho/，Vercel 会错误；如果永远从 / 开始，GitHub Pages 又会丢失子路径。主题因此统一使用 url_for 生成站内地址，使用 full_url_for 生成 SEO 所需的绝对地址。

robots.txt 和 Web App Manifest 也不是静态复制，而是由生成器读取当前 url 与 root 后输出。生成 sitemap 绝对地址时，代码还会判断 URL 是否已经包含 root，避免产生 /ryuho/ryuho/。路径正确性是 SEO 的基础，不是部署完成后的附加修补。

实践：页面语义覆盖搜索与分享

当前布局为所有页面输出：

  • description 与可用时的 keywords
  • canonical
  • Open Graph 标题、摘要、类型、URL、站点名和图片
  • Twitter 大图卡片与图片
  • author、generator 和主题色
  • JSON-LD 结构化数据

文章页还会增加发布时间、更新时间和每个 article:tag。JSON-LD 对文章使用 BlogPosting，其他页面使用 WebSite，并提供标题、描述、URL、图片、关键词、作者和发布日期等当前能够确认的信息。

这里有一个重要取舍：结构化数据只写站点真实拥有的字段，没有虚构组织、评分、浏览量或评论数量。SEO 不应成为制造信息的借口。缺少的数据宁可不输出，也不要为了看起来完整而编造。

404 页面则明确输出 noindex, follow。它仍允许链接被继续发现，但不会把错误页面当成正常内容参与索引。

实践：让搜索引擎能够发现完整站点

单页元数据之外，本站还生成三类站点级入口。

第一是 sitemap.xml。它列出站点 URL，审计不仅确认文件存在和包含地址，还会把每个目标路径映射到构建目录，检查页面真实生成。一个格式正确但包含失效链接的 sitemap 仍然不合格。

第二是 robots.txt。它允许抓取，并提供当前环境下的 sitemap 绝对地址。审计会确认存在 Sitemap:，并专门阻止 GitHub Pages 地址重复 root。

第三是 Atom RSS。页面 head 中通过绝对地址声明 feed，站点也检查 atom.xml 必须存在。RSS 不等同于搜索排名，但它是内容发现与订阅的稳定入口，也帮助站点保持机器可读的发布记录。

站内信息架构同样属于 SEO。首页链接专题、项目和最新文章；分类、标签、归档、相关推荐和正文链接构成内部网络。审计会扫描所有 HTML 的 href 与 src，忽略外部域名、邮件和锚点，然后确认站内目标在构建产物中可达。

取舍：不把 keywords 和“SEO 分数”当目标

本站会输出 keywords，但没有把它当作核心排名手段。它主要复用已经存在的标签、分类和写作方向，让页面主题保持一致。真正重要的仍是清楚的标题与摘要、稳定 URL、可抓取链接和有实际内容的正文。

项目也没有引入在线 SEO 扫描服务作为发布依赖。当前检查使用 Node.js 标准库直接读取 public，能在本地和 CI 中重复执行。它无法模拟搜索引擎的全部行为，也不会承诺排名结果，但能阻止确定性的工程错误上线。

同样，站点没有为每篇文章生成独立社交图片，而是使用文章 cover 或主题默认 hero 图。当前内容规模下，统一图片已经满足分享元数据完整性；只有在文章视觉识别真的成为需求时，才值得增加生成流程。

验证：从“标签存在”升级为“链路成立”

当前审计对 SEO 的验证不是只在首页搜索几个字符串。

它会检查首页是否同时拥有 description、keywords、Open Graph、Twitter Card、canonical、Apple Touch Icon 和 JSON-LD；扫描全部非 404 HTML 是否有 canonical、description 与 Open Graph URL；检查文章页是否公开 article:tag 和 Twitter 图片；确认 404 为 noindex。

站点级检查还覆盖 robots、sitemap、manifest 图标类型、首页最新文章入口、内部链接、静态资源和 sitemap 目标。两条构建命令分别使用 GitHub Pages 与 Vercel 配置，再运行同一套审计。

这种验证不能证明搜索引擎一定收录，也不能证明某个关键词会获得排名。它能证明的是：站点向外提供的标题、摘要、URL、发现入口和内部关系在构建产物中彼此一致。

结论

静态站点的 SEO 不是在模板里堆几个 meta 标签，而是一条从内容源到公开 URL 的完整链路。

文章需要明确标题、摘要、主题和封面；模板需要输出 canonical、分享元数据与结构化数据；站点需要 sitemap、robots、RSS 和可达的内部链接；多环境部署需要根据当前 root 生成正确地址；最后还要从 public 产物验证这些承诺真的成立。

SEO 中可控的部分，本质上是内容质量、信息架构和工程正确性。本站不承诺无法验证的排名结果，只把能够确定的基础做好，并让它们在每次发布时自动接受检查。这比一次性“优化标签”更适合长期维护。
