个人静态站的离线策略：为什么选择网络优先

2026-07-27 5 分钟阅读 2298 字
工程实践 PWA 性能优化 前端体验
查看归档

给个人静态站加 service worker 很容易，难的是先回答一个问题：它到底要解决什么？

如果只是为了让浏览器开发者工具里出现一个绿色标记，service worker 很快会变成额外维护负担。这个博客引入它的目标很具体：

  • 常用入口和最近文章在弱网或断网时仍有机会打开。
  • 正常联网时优先拿到最新内容。
  • 不缓存写操作和跨域响应。
  • GitHub Pages 子路径与 Vercel 根路径使用同一套生成逻辑。
  • 每次发布后旧缓存能被确定清理。

基于这些边界，最终选择的是“核心资源预缓存 + 请求网络优先 + 失败时回退缓存”。

为什么不是缓存优先

静态站的 CSS、JavaScript 和图片很适合缓存优先，但文章页面有一点不同：发布之后可能修正文案、更新链接、补充内容。

如果 HTML 长期缓存优先，读者可能一直看到旧版本。个人博客没有复杂的版本协商和后台刷新提示，缓存过于激进反而会让内容更新变得不可预测。

network-first 的规则更符合这里的优先级：

  1. 先请求网络。
  2. 请求成功就返回最新响应。
  3. 同源且成功的响应写入缓存。
  4. 网络失败时，尝试返回之前缓存的版本。

在线时保持新鲜，离线时尽量可读。它不是性能最激进的方案，但维护语义很清楚。

在构建时决定预缓存列表

service worker 不是固定手写文件，而是 Hexo 构建生成器的一部分。

生成器能读取当前站点的 root 和所有文章，因此可以根据部署环境构造正确路径。预缓存列表包括：

  • 首页、归档、分类、标签和关于页
  • 专题总览与两个专题页
  • 项目页和搜索页
  • RSS、sitemap、manifest 和搜索索引
  • CSS、JavaScript、头像和首页图片
  • 按日期排序的最新 12 篇文章

为什么只放最新 12 篇，而不是全部文章？

预缓存越多，首次安装越慢，任何一个资源失败都可能让安装阶段失败。最近文章是最可能被访问的内容，历史文章则可以在用户正常访问后由运行时缓存补充。

这是一个简单的热内容假设，不需要额外统计系统。

root 必须来自当前部署配置

这个站点有两种部署方式：

  • GitHub Pages：/ryuho/
  • Vercel：/

如果 service worker 里写死 /css/style.css，GitHub Pages 会找不到资源；写死 /ryuho/css/style.css，Vercel 又会错误。

生成器会先把 Hexo 的 root 规范成以 / 结尾，再为每个预缓存路径添加当前 root。最新文章则直接读取 Hexo 生成的 permalink 路径。

同一个源码在两套配置下生成不同但正确的 sw.js。

这也是为什么 service worker 必须进入双部署审计，而不是只在本地浏览器里“试过能用”。

安装阶段为什么使用 addAll

安装时使用 cache.addAll(PRECACHE_URLS)。

它的优点是严格：核心资源中只要有一个无法请求，预缓存就不会悄悄留下不完整状态。对核心入口来说，这种失败比“安装成功但关键页不在缓存里”更容易发现。

严格也意味着构建流程必须提前验证所有路径。当前站点审计会检查：

  • 专题和项目页确实生成。
  • 内部链接与资源都能解析到产物。
  • service worker 包含约定的核心路由。
  • GitHub Pages 和 Vercel 两种 root 下都能通过。

service worker 的可靠性，不只来自它自己的代码，也来自生成前后的配套检查。

每次构建为什么生成新缓存名

缓存名包含构建时生成的时间戳：

新版本 service worker 激活时，会列出当前域名下的缓存，删除所有不等于当前名称的旧缓存，然后调用 clients.claim() 接管页面。

这种方式很直接：

  • 每次部署都会使用新缓存空间。
  • 旧文章、旧 CSS 和旧索引不会无限堆积。
  • 不需要人工维护版本号。

代价是每次构建都会重新预缓存核心资源。对于资源规模很小、发布频率不高的个人博客，这是可接受的交换。

fetch 阶段守住哪些边界

运行时只处理 GET 请求。

即使当前站点几乎没有写操作，这个判断仍然重要：service worker 不应该尝试缓存表单提交、未来的 API 写请求或其他有副作用的操作。

网络请求成功后，也只会缓存：

  • response.ok 为真
  • 请求 URL 与站点同源

这避免把第三方资源和错误响应混进站点缓存。跨域图片或外部脚本仍按浏览器默认方式工作，不由这个 service worker 接管存储。

这套方案不是什么

它不是完整的离线应用。

当前实现没有：

  • 专门的离线提示页面
  • 后台同步
  • 缓存空间上限管理
  • 按资源类型拆分策略
  • stale-while-revalidate
  • 用户可见的更新提示

当用户离线访问一个从未打开、也不在最新 12 篇中的历史文章时，仍然无法得到内容。

这些不是遗漏，而是当前需求边界。博客需要的是基本韧性，不是把静态站改造成复杂客户端应用。

什么时候值得升级

只有出现真实信号时，才值得扩展策略：

  • 用户经常在移动网络或离线环境阅读。
  • 文章和图片规模增长，预缓存明显拖慢安装。
  • 旧缓存导致过真实的内容一致性问题。
  • 需要明确通知用户“新版本已可用”。
  • 搜索或专题希望完全离线工作。

那时可以考虑按资源类型拆分缓存、为 HTML 增加更新提示，或者引入 Workbox 管理更复杂规则。

在此之前，当前实现的优势是每一行都容易解释。

最后的判断

service worker 不是静态站的必选项。它只有在目标、缓存范围、更新策略和失败边界都明确时才值得存在。

这个博客选择 network-first，不是因为它在所有场景下最好，而是因为这里更在意内容新鲜度，同时希望弱网时保留一次读过的页面。

工程上的“够用”不是少做，而是知道哪些能力现在必须可靠，哪些复杂度可以等真实需求出现后再承担。
