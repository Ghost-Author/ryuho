从能构建到敢发布：为 Hexo 博客建立质量门禁

2026-07-27 5 分钟阅读 2083 字
工程实践 Hexo CI/CD 质量工程
查看归档

静态博客最容易给人一种错觉：只要 hexo generate 没报错，发布就算成功。

但“成功生成文件”和“这些文件可以放心上线”是两件不同的事。模板里可能泄漏 undefined，文章可能缺少 description，内部链接可能指向不存在的路径，GitHub Pages 子路径可以正常工作，换到 Vercel 根路径后却全部错位。

这个博客的工程化改造，最后没有停在“构建通过”，而是建立了一套覆盖站点产物、内容源文件和两种部署配置的发布门禁。

问题是如何逐步暴露的

最开始只需要确认一件事：

如果命令退出码是 0，就认为站点可用。随着页面和功能增加，这个判断越来越不可靠。

实际遇到的问题包括：

  • Hexo 模板渲染报错，但部分页面仍然被生成。
  • canonical URL 在子路径部署时出现重复路径。
  • robots.txt 在 GitHub Pages 和 Vercel 上需要不同的 sitemap 地址。
  • manifest 的 start_url 写死后，只适用于一种部署方式。
  • 首页链接看起来正常，目标页面却没有生成。
  • 文章正文、标签和描述可以为空，但构建仍然成功。
  • 图片扩展名和真实文件格式可能不一致。
  • 搜索、专题和 service worker 新增后，缺少对应回归检查。

这些问题有一个共同点：它们通常不会被 Hexo 的构建过程视为错误。

第一层：检查必须存在的产物

最基础的门禁，是确认关键文件真的生成了：

  • 首页和 404 页面
  • RSS 与 sitemap
  • robots 与 Web App Manifest
  • 本地搜索页和搜索索引
  • service worker
  • 专题页与项目页
  • CSS、JavaScript 和核心图片

这一步很简单，但能立刻发现生成器未加载、路径拼错或页面被意外删除的问题。

审计脚本没有引入额外测试框架，而是使用 Node.js 标准库读取 public 目录。对这样一个小型静态站点来说，保持工具简单比增加抽象更重要。

第二层：检查页面是否“像一个可发布页面”

文件存在还不够。每个 HTML 页面还需要具备基本发布质量：

  • canonical URL
  • description
  • Open Graph URL
  • 首页结构化数据
  • 文章分享图片和 article tags
  • 404 页的 noindex

审计还会扫描生成后的 HTML，阻止 undefined、null、默认 Hexo 文案和空日记模板进入产物。

这类检查的价值不在于“SEO 分数”，而在于把模板错误从人工浏览变成确定的构建失败。

第三层：验证链接和资源真正可达

静态站点很适合做全量内部链接检查，因为所有目标最终都在 public 目录里。

审计脚本会收集页面中的 href 和 src，忽略邮件、锚点和外部域名，然后把站内 URL 转换成相对产物路径。目标既可能是一个文件，也可能是目录下的 index.html。

这一层会验证：

  • 页面之间的导航
  • 图片与脚本资源
  • 首页最新文章入口
  • sitemap 中列出的 URL
  • GitHub Pages /ryuho/ 子路径
  • Vercel / 根路径

真正困难的不是写正则，而是正确处理两套 root。解决方式是让 robots、manifest、搜索索引和 service worker 都从 Hexo 当前配置生成，不再维护两份静态文件。

第四层：把内容质量放进构建流程

技术博客的质量问题不只来自代码，也来自内容。

现在每篇文章至少需要：

  • title 和 date
  • 足够具体的 description
  • 至少两个 tags
  • 至少一个 category
  • 可用 cover
  • 不是提纲或占位文本的正文

脚手架也接受同样检查，避免新文章从一开始就生成空的元数据字段。

这不能判断文章观点是否精彩，但能挡住最常见的发布疏漏。内容判断仍然由作者负责，机器只守住可确定的底线。

双部署如何进入同一套验证

项目保留了两条发布路径：

第一条使用 GitHub Pages 的 /ryuho/ 子路径，第二条合并 Vercel 配置并使用 / 根路径。两条命令最终运行同一个审计脚本。

目前完整检查包含 47 项规则，会扫描 37 个 HTML 页面。构建后的图片优化还能把核心图片减少约 293 KiB。

数字本身不是目标。重要的是以后修改模板、文章、搜索或部署配置时，旧能力都有机会被自动验证。

一次人工抽查仍然有价值

自动审计建立后，我仍然保留人工抽查。

有一次所有基础检查都通过了，但 robots.txt 的 sitemap 地址出现了 /ryuho/ryuho/。原因是站点 URL 本身已经带有子路径，生成器又追加了一次 root。

修复之后，这个具体问题也被加入审计。

这件事提醒我：自动化规则不是凭空设计出来的。它通常来自一次真实错误，然后把这次错误变成以后不会重复踩的边界。

最后的取舍

质量门禁不是越多越好。

适合自动化的是确定性问题：文件是否存在、路径是否可达、元数据是否完整、资源是否匹配。文章是否有洞察、专题是否值得写、一个功能是否真的服务读者，仍然需要人的判断。

这个博客进入稳定维护阶段后，不再继续增加没有使用场景的组件。发布流程只保留一个清晰原则：

内容负责提供价值，自动化负责守住底线。

当一次提交同时通过两种部署配置和完整产物审计时，我才真正从“它能构建”走到了“我敢发布”。
